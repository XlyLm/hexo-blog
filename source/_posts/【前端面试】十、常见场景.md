## 一、常见场景

### **1. 设计一个能渲染万级数据的列表，怎么做？**

考察点：是否知道虚拟滚动与渲染瓶颈。思路：只渲染可视区 + 缓冲区（上下各若干行），用容器占位撑起总高度，滚动时按 `scrollTop` 计算起始索引并做绝对定位偏移；行高固定时最简单（可精确计算），行高不定时用预估高度 + 动态测量与位置缓存修正；配合 `requestAnimationFrame` 合并滚动更新、`ResizeObserver` 处理容器变化。易错边界：滚动条抖动、动态高度导致的跳动、快速滚动出现空白、删除行后的位置重算。

### **2. 表格有几万行还有固定列、合并单元格，怎么优化？**

分层：数据层分页或虚拟滚动（二者选一，不要叠加）、列层只渲染可视列（横向虚拟化）、渲染层用 Canvas 或轻量单元格组件（避免每格一个重量级组件）、交互层冻结列用 CSS `sticky` 而非复制一份表格、合并单元格在可视区计算后再合并（不可全量计算）。易错边界：`sticky` 与横向滚动、键盘操作与虚拟滚动的选区同步、合计行与虚拟滚动的冲突。

### **3. 搜索联想怎么做才不出现请求错乱？**

三件事：**防抖**（输入停止 300ms 再查）、**取消**（新请求发出前 `abort` 旧请求，或用请求序号丢弃过期响应）、**缓存**（同关键词命中本地缓存，前缀命中可做本地过滤）。进阶：输入法组合期（`compositionstart/end`）不触发查询、空关键词直接清空、失败时降级到本地历史。易错边界是“后发请求先返回”导致结果显示成旧关键词的结果，这是最典型的竞态。

### **4. 动态表单怎么设计？**

分层：**schema 驱动**（字段类型、校验规则、联动关系、布局都写成配置）、**状态层**（值、错误、触碰状态分开管理）、**渲染层**（按类型映射组件）。关键细节：校验时机（失焦校验、提交全量校验、修改后清除错误）、错误定位（提交失败滚动到第一个错误字段并聚焦）、联动（A 字段变化清空 B 的值与错误）、性能（大表单用非受控 + 局部订阅，避免每次输入全表重渲染）。

### **5. 权限系统怎么设计？**

三层缺一不可：**路由级**（登录后拉取菜单与路由表，动态 `addRoute`，无权限路由不注册）、**按钮级**（指令或组件包装，按权限码控制显隐）、**接口级**（服务端必须校验，前端控制只是体验）。要点：权限码集中管理避免硬编码散落、刷新后重建路由（不要在 `router.beforeEach` 里反复拉）、无权限要有明确提示而非白屏、超级管理员与降级兜底。必须说清“前端权限不可信”。

### **6. 组件库里的弹窗/抽屉怎么统一管理？**

问题：命令式调用（`Modal.confirm()`）与声明式组件并存、多层弹窗层叠顺序、卸载后残留、SSR 下不能操作 DOM。方案：单例管理器维护弹窗队列与 z-index 分配、命令式 API 内部创建实例并在关闭时真正销毁、用 Portal/Teleport 挂到 body 避免被父级 `overflow` 裁剪、多个弹窗按栈管理（Esc 只关最上层）、焦点管理（打开时聚焦、关闭时还原）。易错边界：路由切换时批量关闭、弹窗内的异步操作在关闭后回调（用 token 校验）。

### **7. 无限滚动加载怎么做稳？**

用 `IntersectionObserver` 监听底部哨兵元素（比监听 `scroll` 更省），命中后加载下一页；维护 `loading` 与 `hasMore` 双标志避免重复请求；失败要能重试而不是静默卡住；列表变化后重新观察（元素被替换）。易错边界：内容不足一屏时不会触发（需主动加载直到填满）、快速滚动触发多次、分页接口返回重复数据（按 id 去重）、卸载后 observer 未断开导致泄漏。

### **8. 大文件上传的完整方案？**

分片（`Blob.slice`，15MB/片）→ 计算文件 hash（可用抽样 hash 加速）→ 询问服务端是否已存在（**秒传**）与已上传分片列表（**断点续传**）→ 并发上传（限制 35 并发）→ 单片失败重试（指数退避）→ 全部分片到齐后请求合并并校验整体 hash。细节：进度按已完成分片字节数计算（不是分片数）、暂停即 `abort` 在途请求、取消要通知服务端清理临时分片、上传中禁止页面刷新丢失状态（可持久化到 `IndexedDB`）。

### **9. 主题切换（含深色模式）怎么做？**

用 CSS 变量集中定义色板（`:root` 与 `[data-theme=dark]`），切换只改根节点属性；选择存 `localStorage` + 跟随系统（`prefers-color-scheme`）；组件内颜色全部走变量，避免散落硬编码；ECharts/Canvas 这类非 CSS 内容需要监听主题变化重新 `setOption`。易错边界：SSR 首屏闪白（需服务端或内联脚本提前注入主题）、切换时有过渡导致闪烁（切换瞬间禁用 `transition`）、图片与阴影在深色下的可读性。

### **10. 埋点系统怎么设计？**

两种接入：声明式（指令/组件属性，如 `data-track`）适合简单点击；命令式（`track(event, props)`）适合业务事件。工程要点：公共属性自动附加（页面、用户、版本、设备）、批量上报（队列 + 定时/阈值 + `sendBeacon` 兜底）、采样与去重、失败本地暂存后补偿、埋点表与代码分离（用常量枚举避免拼错）、开发环境可视化调试。易错边界：上报阻塞主流程、重复埋点、隐私字段泄露。

### **11. 前端监控 SDK 怎么设计？**

四类采集：异常（`window.onerror`、`unhandledrejection`、资源错误、框架错误钩子）、性能（`PerformanceObserver` + 首屏与交互指标）、白屏（采样关键点像素或检测根节点是否为空）、行为（面包屑：点击、路由、请求序列）。设计要求：体积小（SDK 进首屏关键路径）、采样与限流、脱敏、离线缓存重发、**版本号与 sourcemap 关联**用于还原堆栈、以及可配置的开关。易错边界：SDK 自身报错导致循环上报、采集影响性能（需要 `requestIdleCallback` 异步处理）。

### **12. 弱网与断网怎么处理？**

检测（`navigator.onLine` + 主动探测，不只看 onLine）、降级（超时缩短、图片降级、关闭非必要请求）、重试（仅幂等请求 + 指数退避）、提示（明确的离网条与手动重试入口）、缓存（接口结果本地缓存 + `stale-while-revalidate` 策略）、离线可用（Service Worker 缓存关键资源与页面）。易错边界：重试风暴、离线时的写操作丢失（需队列化并在恢复后同步）、缓存过期导致展示脏数据。

### **13. 分享海报生成怎么做？**

用 Canvas 绘制：底图 + 头像（圆形裁剪）+ 文字（需手动实现换行与省略）+ 二维码。关键细节：**图片必须跨域可用**（`crossOrigin='anonymous'` 且服务端允许，否则画布被污染无法导出）、按 DPR 放大画布保证清晰度、字体加载完成后再绘制（`document.fonts.ready`）、长文本按宽度断行并计算行高、最终 `toDataURL`/`toBlob` 输出（移动端注意长按保存的限制）。易错边界是“本地预览正常、真机上文字错位”（字体与 DPR 差异）。

### **14. 国际化怎么落地？**

文案抽离到 key（禁止中文硬编码在组件里）、按语言分包动态加载（`import()` 按 locale）、支持插值与复数规则（不同语言复数形态不同）、日期/货币/数字用 `Intl` 而非手写格式化、RTL 语言需要布局镜像（用逻辑属性 `margin-inline` 而非 `margin-left`）。工程要点：缺 key 的兜底与告警、文案变更走产品确认、翻译文件纳入版本管理。

### **15. 微前端要怎么落地才不踩坑？**

先问“为什么”：是否需要**独立构建与发布**（这是唯一硬理由，技术炫技不是）。方案分两类：iframe（隔离最彻底、体验代价大）、运行时组合（qiankun/Module Federation，隔离与共享需要权衡）。落地要点：主子应用路由约定（`activeRule` 与 basename 不冲突）、公共依赖共享（避免多实例）、通信（`initGlobalState` 单向 + 事件，注意可序列化）、样式隔离（前缀或 Shadow DOM）、鉴权与埋点统一入口、灰度与回退能力（能一键下线子应用）。

## 二、难题

### **1. 万级节点的树形组件怎么优化？**

三步：**数据结构扁平化**（`Map<id, node>` + 父 id，避免深层递归与重复遍历）、**虚拟滚动**（只渲染展开且可见的节点，展开状态与选中状态独立维护）、**按需计算**（勾选联动用扁平表 + 索引而非递归查找，父子半选状态用集合运算）。交互细节：展开/折叠只更新可见集合、搜索时先过滤再定位并自动展开路径、拖拽排序只改局部关系。易错边界是“全选/半选”的递归计算在万级数据下直接卡死，必须改成自上而下的索引更新。

### **2. 实时协同编辑的技术选型怎么讲？**

核心是**冲突解决模型**：OT（操作转换，需中心服务器串行化，实现复杂但状态小）、CRDT（无冲突合并，天然支持离线与多端，代价是数据结构与内存开销）。配套：WebSocket 长连接 + 心跳 + 断线重连、光标与选区共享（`awareness` 协议）、离线队列与重放、版本快照与历史回滚。工程现实是该用成熟方案（Yjs/Automerge）而不是自研，自研的成本主要在边界情况（并发删除、撤销栈合并）。

### **3. 线上白屏怎么系统性排查？**

按链路分四层定位：**网络层**（DNS/CDN/证书/跨域、请求是否 200、HTML 是否被劫持）、**资源层**（JS/CSS chunk 404、hash 版本不匹配、`integrity` 失败）、**代码层**（语法错误、兼容性（旧浏览器不支持新语法）、初始化异常、未捕获 Promise）、**渲染层**（首屏依赖接口超时、SSR 直出内容缺失、样式导致内容不可见）。手段：监控里看“页面上报率突降”（白屏特征）、版本号与发布时间比对（是否本次发布引入）、灰度分批验证、以及预案（入口 HTML 保留旧版本资源一段时间、增加“检测到白屏自动上报 + 兜底提示页”）。

### **4. 前端灰度方案怎么设计？**

四个要素：**灰度维度**（用户 id hash、地域、设备、白名单、随机比例）、**分流位置**（构建级：发布不同产物；运行时级：配置中心下发开关，同一份代码跑不同逻辑）、**观测**（灰度组与对照组的错误率、核心转化指标对比）、**回滚**（开关秒级关闭 / 版本回退）。最佳实践是“代码发布与功能开启解耦”（用 feature flag），灰度只控制开关而不是控制产物，这样回滚不需要重新构建。易错边界是灰度规则的前端缓存（配置要能强制刷新）与灰度用户的数据一致性（同一用户不能在新旧逻辑间反复横跳）。

### **5. 十万级数据点的图表怎么保证流畅？**

分层：数据层**降采样**（LTTB 等保形算法，按像素宽度决定保留点数）、渲染层用 Canvas（ECharts 的 `large` 模式）或 WebGL、交互层只对可视区（`dataZoom`）重算、更新层用增量 `setOption`（只改 `series.data`，不重建 option）。易错边界：缩放后精度丢失（需按区间重新请求原始数据）、图例与 tooltip 的命中计算在大数据下变慢（需空间索引或简化）、内存随历史数据累积（旧实例必须 `dispose`）。

### **6. 复杂业务的状态管理怎么分层？**

先分**服务端状态**与**客户端状态**：服务端状态交给请求库（缓存、失效、重试、乐观更新），不要塞进全局 store 手动同步；客户端状态再按更新频率分层：组件内 `useState` → 页面级 Context/store → 跨页面全局（Pinia/Zustand）。设计要点：状态形状扁平化、派生数据用计算属性而非冗余字段、异步流程用状态机（`idle/loading/success/error` 显式建模）、副作用集中管理便于测试。判断“设计是否过度”的标准是有没有人为同步两份数据。

### **7. 无障碍与键盘操作怎么做到可用？**

六个必做项：语义化结构（标题层级、`aria-label`、`role`）、键盘可达（所有交互可 Tab，弹窗内**焦点陷阱**、关闭后焦点还原）、焦点可见（不要用 `outline: none` 抹掉焦点环）、快捷键与 Esc 约定、颜色不是唯一信息载体（对比度达标、错误不只靠红色）、屏幕阅读器播报（动态内容用 `aria-live`）。验证方式是真机用 Tab + 读屏器走一遍核心流程，而不是只看 ESLint 的 a11y 规则通过。

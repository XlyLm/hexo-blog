# 一、Webpack

## 1、常见题

### **1. Webpack 的核心概念有哪些？**

`entry`（入口，起点模块）、`output`（产物路径与文件名）、`loader`（把非 JS 资源或新语法转换成模块）、`plugin`（在构建生命周期上挂载能力，如压缩、抽离 CSS、注入变量）、`mode`（development/production，决定内置优化与 `DefinePlugin` 的默认值）、`devtool`（source map 策略）、`resolve`（模块解析规则）、`optimization`（分包与压缩）。

### **2. loader 和 plugin 有什么区别？**

loader 是**模块级**转换函数：输入源码字符串或 AST，输出新内容，只在模块加载阶段工作（`babel-loader`、`css-loader`）。plugin 是**构建过程级**扩展：基于 Tapable 的事件钩子（`compiler.hooks` 编译级、`compilation.hooks` 单次构建级），能做产物改写、文件生成、注入变量等 loader 做不到的事（`MiniCssExtractPlugin`、`HtmlWebpackPlugin`、`DefinePlugin`）。

### **3. loader 的执行顺序是怎样的？**

`use` 数组从**右到左、从下到上**执行（`['style-loader','css-loader']` 先 css 再 style）；`enforce: 'pre' | 'post'` 可插队到普通 loader 之前或之后；`pitch` 阶段则相反从左到右，且 `pitch` 有返回值时会跳过剩余 loader。`inline` loader（`!` 前缀）与 `!`/`-!`/`!!` 可控制是否叠加配置中的 loader。

### **4. 说一下 Webpack 的构建流程。**

Webpack 的构建流程本质上是一个**串行的、基于事件驱动的过程**。它从读取配置开始，通过 `Compiler` 和 `Compilation` 对象调度，递归地解析和转换模块，最终将结果组装成 Chunk 并写入文件系统。整个过程可以清晰地划分为**初始化、编译构建、输出**三大阶段。

- **第一阶段：初始化**

​	这个阶段主要是在为后续的编译工作做准备，核心是创建全局唯一的 `Compiler` 实例。

​	**合并配置参数**：从配置文件（如 `webpack.config.js`）和命令行 Shell 语句中读取参数，并将它们合并为最终的配置对象。

​	**实例化 Compiler**：用上一步的参数初始化 `Compiler` 对象。`Compiler` 是 Webpack 的全局调度中心，它包含了完整的配置信息，并负责管理整个构建生命周期。

​	**加载插件**：遍历配置中的 `plugins` 数组，依次调用每个插件的 `apply` 方法，并将 `Compiler` 实例传入。插件通过这种方式在 Webpack 的生命周期钩子（hooks）上注册监听，从而介入构建过程。

​	**准备环境**：触发 `environment`、`afterPlugins`、`afterResolvers` 等钩子，完成文件系统适配、模块解析器（Resolver）初始化等预备工作。

- **第二阶段：编译构建（核心）**

​	这是最复杂的一步。Webpack 会从入口文件出发，递归地找出所有依赖，并用 Loader 对每个模块进行转换。

​	**启动编译**：调用 `Compiler.run()` 触发 `run` 钩子，随后创建 `Compilation` 对象。`Compilation` 是单次构建的执行者，负责管理本次构建的所有模块和资源。

​	**从 Entry 出发**：根据配置的 `entry`，找到入口文件。Webpack 会为每个入口创建一个对应的 `EntryPlugin`，为递归解析做准备。

​	**递归编译模块（Make 阶段）**：这是流程中最耗时的一环。

- **第三阶段：输出**

​	这个阶段负责将内存中生成的 Chunk 转换成最终的文件，并写入磁盘。

​	**生成资源**：根据 `output` 配置（如 `filename`、`path`），为每个 Chunk 生成对应的最终文件内容。此时会触发 `emit` 钩子，这是**修改输出文件内容的最后机会**。

​	**写入文件系统**：将生成的文件内容实际写入到 `output.path` 指定的目录中。完成后触发 `afterEmit` 钩子。

​	**完成构建**：整个流程结束，触发 `done` 钩子。如果在任何阶段发生错误，则会触发 `failed` 钩子并终止流程。

### **5. 手写一个简单 loader 要注意什么？**

签名是 `function (source) { return transformed }`；需要异步或多次回调时用 `this.async()` 返回的 callback，或返回 Promise；用 `this.query`/`this.getOptions()` 拿配置；`this.resourcePath` 判断目标文件；注意 loader **必须是无状态、可并行的纯转换**，不要在里面做副作用。若要处理 source map，用 `this.callback(null, code, map)` 透传。

### **6. 手写一个 plugin 的要点？**

一个类（或函数）带 `apply(compiler)`；在合适的钩子上 `tap/tapAsync`，同步钩子用 `tap`，异步用 `tapAsync/tapPromise`；`compiler.hooks.emit` 阶段可改 `compilation.assets` 新增文件；`compilation.hooks.processAssets` 是 webpack 5 推荐的改产物位置。`plugin` 的名字用于性能分析识别。

### **7. HMR（热更新）的原理是什么？**

编辑文件 → `webpack-dev-server` 触发增量编译，生成 `*.hot-update.js` 与 `*.hot-update.json` → 通过 WebSocket 把新 hash 通知浏览器 → 浏览器的 HMR runtime 用 JSONP 拉取更新清单 → 对比 `module.hot` 的接受逻辑，逐模块替换（`module.hot.accept`），替换失败则向上冒泡到入口，最终整页 reload。框架靠 loader 自动注入 accept 逻辑（Vue 的 `vue-loader`、React 的 `react-refresh`），所以“改代码局部生效”不是 webpack 的默认行为，而是模块自己声明了可接受更新。

### **8. 如何做构建速度优化？**

缩小范围：`resolve.extensions` 精简、`alias` 减少查找、`module.noParse` 跳过无依赖的大文件、`exclude` 排除 `node_modules`。并行与缓存：`cache: {type:'filesystem'}` 持久化缓存、`babel-loader` 的 `cacheDirectory`、`thread-loader`。减少工作量：`transpileOnly`（ts-loader 配 `fork-ts-checker` 单独做类型检查）、生产环境关闭 source map 或换 `cheap`。定位工具：`speed-measure-webpack-plugin` 看每个环节耗时，`--profile` 生成 stats。

### **9. 如何做产物体积优化？**

分包（`splitChunks` 拆 vendor 与公共模块、`runtimeChunk: 'single'`）、按需加载（动态 `import()` 生成异步 chunk）、tree shaking（ESM + `sideEffects: false`）、压缩（`TerserPlugin` 去 console/debugger、`CssMinimizerPlugin`）、按需引入组件库（`babel-plugin-import` 或 ESM 直接引入）、CDN 外置（`externals` 把 React/Vue 留在全局）、gzip/brotli 预压缩。分析工具：`webpack-bundle-analyzer` 看体积分布。

### **10. `splitChunks` 怎么配？**

关键项：`chunks: 'async' | 'initial' | 'all'`（`all` 才能覆盖同步依赖）、`cacheGroups`（按 `test` 或模块路径归组、`priority` 决定优先级、`reuseExistingChunk`）、`minSize/minChunks/maxAsyncRequests/maxInitialRequests`。典型配法：`vendor` 组收 `node_modules`，`common` 组收被两个以上 chunk 引用的业务代码，并注意把框架与业务拆开以便缓存（框架更新频率低）。

### **11. tree shaking 的原理和生效条件？**

原理：基于 ESM 的**静态结构**在编译期分析导出与引用关系，标记未使用的导出（`usedExports`），交给 `terser` 在压缩阶段删除；同时 `sideEffects` 声明整个模块“无副作用”时可整体跳过。生效条件：必须是 ESM（`babel` 的 `modules: false`，不能转成 CJS）、`mode: 'production'`、`usedExports` 与 `minimize` 开启、未被 `require` 或副作用调用破坏。`/*#__PURE__*/` 注解可帮助判断函数调用无副作用。

### **12. `hash`、`chunkhash`、`contenthash` 有什么区别？**

`hash` 与整个构建相关（任一文件变化全变）、`chunkhash` 与入口 chunk 内容相关、`contenthash` 与**文件自身内容**相关。产物文件名应该用 `contenthash` 才能做到“改 A 只让 A 的缓存失效”。注意 `runtimeChunk` 要单独抽出，否则 runtime 里维护的 chunk 映射变化会让业务 chunk 的 `contenthash` 也变。

### **13. source map 的几种取值怎么选？**

按“质量 vs 速度”取舍：`eval` 最快但只映射到模块边界；`cheap` 不含列信息、速度快；`module` 使用 loader 转换前的源码（Babel/TS 项目必需）；`inline` 内嵌 base64 增大体积；`hidden` 生成但不写引用（配合上报平台）。生产一般 `source-map`（不外泄）或 `hidden-source-map` 上报错误监控，开发用 `eval-cheap-module-source-map`。

### **14. 缓存怎么配才对？**

`cache: { type: 'filesystem', buildDependencies: { config: [__filename] } }` 让二次构建复用模块与代码生成结果；`babel-loader` 加 `cacheDirectory`；产物层面用 `contenthash` + 长缓存（HTML 不缓存、静态资源缓存一年）；`node_modules` 单独拆 vendor chunk。注意改 webpack 配置或 loader 版本后要能识别失效（`buildDependencies` 与 `cache.version`）。

### **15. `resolve` 有哪些常用配置？**

`alias`（路径别名，减少深层相对路径、也避免大小写问题）、`extensions`（顺序影响解析优先级，越靠前越快）、`modules`（查找目录，如 `node_modules`）、`mainFiles`、`symlinks`、`fallback`（浏览器端 polyfill 的降级路径）。对了还有 `resolve.extensionAlias`（处理 ESM 的 `.js` 后缀映射到 `.ts`）。

### **16. `devServer` 常用能力有哪些？**

`hot`、`port`、`open`、`static`（静态目录）、`proxy`（跨域代理，`changeOrigin`、`pathRewrite`）、`historyApiFallback`（SPA 路由回退到 index.html）、`client.overlay`（编译错误覆盖层）、`https`、`headers`。`proxy` 只解决开发环境跨域，生产要靠网关同源或 CORS。

### **17. 多环境配置怎么组织？**

基础配置 `webpack.common.js` + `webpack.dev.js` + `webpack.prod.js`，用 `webpack-merge` 合并；环境差异用 `mode`、`DefinePlugin` 注入 `process.env`、`dotenv` 读 `.env` 文件；`publicPath` 按部署路径配置。禁忌是把密钥写进 `DefinePlugin`（会被打进产物）。

### **18. asset modules 是什么？**

Webpack 5 取代 `file-loader/url-loader/raw-loader` 的内置能力：`type: 'asset/resource'` 输出独立文件、`'asset/inline'` 转 base64、`'asset/source'` 导出源码字符串、`'asset'` 按 `parser.dataUrlCondition.maxSize` 自动选择。配置更简单、少一层 loader，注意体积阈值（默认 8KB）对首屏与请求数的影响。

### **19. `externals` 用来做什么？**

告诉 webpack 某些模块“不要打包”，改为运行时从全局变量或 CDN 取（`externals: { vue: 'Vue' }`）。用于减小体积、复用 CDN 缓存；代价是引入外部依赖的可用性风险（CDN 挂掉就白屏），所以要有兜底（自建 CDN 或本地降级），并且要在 HTML 模板里手动插入对应脚本。

### **20. Webpack 5 有哪些重要更新？**

持久化文件缓存（二次构建显著提速）、asset modules、`Module Federation`（跨应用共享模块）、更好的 tree shaking（`innerGraph` 能分析模块内部导出使用）、长期缓存开箱（`deterministic` 的 chunkId/moduleId）、内置 `terser`、`progress` 与构建统计增强、Node polyfill 默认移除（需要显式 `fallback`）。

## 2、难题

### **1. 为什么 Babel 处理后的代码 tree shaking 会失效？**

tree shaking 依赖 ESM 的静态结构，Babel 默认会把 `import/export` 转成 `require/module.exports`（CJS 是动态的、导出是运行时赋值），webpack 就很难静态判断哪个导出被使用。解决方法是在 Babel 配置里设 `modules: false`，保留 ESM 交给 webpack 处理（这也是 `@babel/preset-env` 的默认行为，但自定义配置常被改掉）。

### **2. `sideEffects` 到底控制了什么？**

它是“模块是否有副作用”的声明（`package.json` 里的 `sideEffects: false` 或数组列举有副作用的文件）。为 false 时 webpack 可以安全地**整体跳过**未被使用的模块（包括顶层副作用代码，比如全局样式注入、polyfill），而不只是删除导出；若模块确实有副作用（如 `import 'xx.css'`、注册全局），必须显式列入数组，否则会被误删。所以它是“激进优化”的开关，配置错误通常表现为样式或初始化逻辑丢失。

### **3. HMR 的模块替换是怎么做到不整页刷新的？**

HMR runtime 拉取到更新后，先找“接受该模块更新的父模块”（`module.hot.accept` 声明的），沿依赖链向上冒泡直到找到接受者；找到后卸载旧模块、执行新模块工厂函数、重新执行接受回调，从而只更新局部状态。若一路冒泡到入口都没人接受，就执行整页 reload。这也是为什么“有些改动能热更新、有些必须刷新”（比如改 store 初始化逻辑、改路由配置）。

### **4. 持久化缓存的失效机制是什么？**

webpack 会为每个模块与代码生成结果计算哈希快照（内容、loader、`resolve` 结果、依赖等），存到 `node_modules/.cache`。下次构建时只有快照变化才重新处理；配置变化通过 `buildDependencies` 与 `cache.version` 纳入失效判断。常见“缓存没生效”的原因是配置文件没被纳入依赖、或 loader 版本变化但未感知（升级 loader 后可手动清缓存）。

### **5. `runtimeChunk` 为什么能让缓存更稳？**

webpack 的运行时代码里维护着“chunk id → 文件名”的映射与异步加载逻辑。若不抽出 runtime，只要任何一个 chunk 的 id 或文件名变化，含 runtime 的入口 chunk 内容就变，其 `contenthash` 跟着变，导致业务代码的缓存失效。抽出为独立 `runtime` chunk 后，业务 chunk 的 `contenthash` 只随自身内容变化，命中率明显提升（同时便于把 runtime 内联到 HTML 减少请求）。

### **6. 循环依赖在 Webpack 里什么时候会炸？**

CJS 场景：A `require` B，B 又 `require` A，B 拿到的 A 是一个“已执行部分代码的 exports 对象”，若此时访问尚未赋值的属性就是 `undefined`，表现为“某些情况正常、某些情况得到空对象”。ESM 场景：静态绑定会在实例化阶段建立，但若在模块顶层以函数调用形式依赖对方尚未初始化的绑定，会因 TDZ 报错。排查手段是 `webpack --stats-error-details` 与循环依赖插件，设计上应该用依赖注入或抽公共模块打破环。

### **7. Module Federation 的原理与风险是什么？**

被远程暴露的模块通过 `remoteEntry.js`（一份运行时可加载的清单）在**运行时**动态加载，`shared` 声明共享依赖并由宿主与远程协商版本（`requiredVersion`、`singleton`），实现“多个独立构建的应用共享同一份 React/Vue”。风险：版本协商失败会重复加载或冲突、依赖必须 `eager` 才能在同步代码里用、远程不可用会让宿主直接报错（需要降级与超时），且构建间的类型与接口约定没有编译期保证。

### **8. Webpack 与 Vite 的本质差异在哪？**

Webpack 是“打包式”：开发时也要构建依赖图并产出 bundle，靠 loader 生态覆盖各种资源。Vite 开发时利用浏览器原生 ESM **按需**请求源码，只对依赖做 `esbuild` 预构建（快是因为不打包），生产用 Rollup 打包。差异带来三点取舍：Vite 冷启动与 HMR 更快，但 dev 与 prod 用两套工具（行为可能不一致）；Webpack 生态与历史配置更成熟、复杂定制能力强（Module Federation、深度分包），但启动与热更新随项目增大而变慢。

# 二、Vite

## 1、常见题

### **1. Vite 是什么，为什么比 Webpack 快？**

利用浏览器原生 ESM 的构建工具：开发阶段**不打包源码**，浏览器请求哪个模块就按需编译返回哪个，因此冷启动时间与项目规模基本解耦；依赖用 esbuild 预构建（Go 编写、多线程并行，速度是 JS 编译器的十倍量级）；HMR 基于 ESM 的模块图只失效相关模块。生产用 Rollup 打包。一句话：快在“不做无用的预先打包 + 用更快的编译器”。

### **2. 「依赖预构建」是干什么的？**

三件事：把 CJS/UMD 依赖转成 ESM（浏览器只认 ESM）；把散碎文件（如 lodash 的众多子模块、按需引入的组件库）合并成单个文件，减少 HTTP 请求数；用 esbuild 并行编译，降低首次请求成本。产物放在 `node_modules/.vite/deps`，文件名带 hash，附 `_metadata.json` 记录解析结果。

### **3. 预构建什么时候会失效重做？**

lockfile 变化（依赖版本变）、Vite 配置或 `optimizeDeps` 项变化、浏览器缓存过期（`?v=hash` 不匹配）。运行时若发现源码里出现未预构建的裸依赖（例如动态路径引入），会**重新预构建并整页刷新**，这是“首次打开项目时页面自己刷一下”的原因。可用 `optimizeDeps.include/exclude` 显式控制，或 `--force` 强制重建。

### **4. 为什么开发用 esbuild、生产用 Rollup？**

esbuild 快在转换与压缩，但插件生态、代码分割策略、CSS 处理与产物控制不如 Rollup 成熟；生产构建更需要稳定精细的分包、tree shaking、CSS 提取与兼容处理，所以选 Rollup。代价是 dev 与 prod 使用两套工具链，行为可能不完全一致（这是 Vite 最大的架构取舍）。

### **5. Vite 的 HMR 原理是什么？**

Dev Server 维护模块图（谁 import 了谁）。文件变化时：先判定该模块是否“可自接受”（代码里有 `import.meta.hot.accept`），否则沿 importer 链向上找最近的接受边界；然后通过 WebSocket 只把需要更新的模块路径与时间戳发给浏览器，浏览器丢弃该模块及其依赖的缓存、重新请求（`?t=timestamp` 绕过缓存）。因此改一个文件不会重新加载整个应用；整链无人接受时才整页刷新。

### **6. Vite 插件和 Rollup 插件是什么关系？**

Vite 的插件容器**兼容 Rollup 插件钩子**（`resolveId`、`load`、`transform`、`buildStart`、`generateBundle` 等），并额外提供开发专用钩子：`config`（改配置）、`configResolved`（拿最终配置）、`configureServer`（挂中间件）、`transformIndexHtml`（改 HTML，可声明 `order: 'pre'|'post'`）、`handleHotUpdate`（自定义 HMR 行为）。注意部分 Rollup 输出阶段钩子只在 build 时执行。

### **7. 插件执行顺序怎么控制？**

用 `enforce: 'pre' | 'post'`：`pre` 在 Vite 核心插件之前，`post` 在之后，默认是中间段。同一 enforce 段内按数组顺序执行。`transform` 阶段按顺序串行，`transformIndexHtml` 可用 `order` 单独控制。

### **8. 环境变量怎么用？**

用 `import.meta.env` 访问（`MODE`、`DEV`、`PROD`、`BASE_URL` 内置）；自定义变量必须以 `VITE_` 前缀才会暴露给客户端（防止把密钥打包进去）；按 `mode` 加载 `.env`、`.env.development`、`.env.production`。改 `.env` 需要重启 dev server。

### **9. 静态资源怎么处理？**

`public/` 下的文件原样拷贝、用绝对路径引用、不参与构建（适合 favicon、不希望被 hash 的文件）；源码里 `import img from './a.png'` 会走构建并返回 URL（小于 `assetsInlineLimit` 的转 base64）；后缀查询 `?url`（拿 URL）、`?raw`（拿源码字符串）、`?inline`（强制内联）；`new URL('./x.png', import.meta.url)` 用于动态路径。

### **10. CSS 相关怎么配？**

预处理器在 `css.preprocessorOptions` 里配（`less.additionalData` 注入变量、`sass` 的 `additionalData`）；CSS Modules 用 `.module.css/.module.less`，`css.modules.localsConvention` 控制导出命名风格；`css.postcss` 读 `postcss.config`；`@import` 支持别名解析。注意生产环境 CSS 会被提取为独立文件，顺序由 import 顺序决定。

### **11. Vite 怎么做 TS 类型检查？**

Vite 只做**转译**（esbuild 直接抹掉类型），不做类型检查。生产环境单独跑 `vue-tsc --noEmit` 或 `tsc --noEmit`（放 CI 或构建前置步骤），配合编辑器的 TS 服务做实时提示。因此必须开启 `isolatedModules`（每个文件独立转译），避免依赖跨文件的类型信息（如 `const enum`、类型再导出的运行时用法）。

### **12. 别名怎么配？**

`resolve.alias` 用 `@` 指向 `src`；同时要在 `tsconfig.json` 的 `paths` 里同步声明，否则类型推导与编辑器跳转失效。若要“后缀自动解析”，`resolve.extensions` 保持默认即可，但 `import 'x'` 不带后缀在 ESM 严格语义下有歧义风险，工程上建议写全后缀或统一用别名。

### **13. 代理和 base 怎么配？**

`server.proxy` 配跨域代理（`target`、`changeOrigin`、`rewrite`），只在开发环境生效；生产要靠网关同源或 CORS。`base` 决定部署子路径（影响资源 URL、`import.meta.env.BASE_URL`、路由 basename），配错会出现“本地正常、部署后白屏”。

### **14. 生产构建怎么分包？**

默认按动态 `import()` 自动切分；需要更细控制用 `build.rollupOptions.output.manualChunks`（把框架、UI 库、图表库分别拆开，利于长缓存）；`build.chunkSizeWarningLimit` 用于告警阈值；`build.assetsInlineLimit` 控制内联阈值。常用的思路是“变化频率越低越靠前拆分”。

### **15. 浏览器兼容怎么处理？**

`build.target` 决定转译目标（默认 `modules`，即主流现代浏览器）；要兼容旧浏览器用 `@vitejs/plugin-legacy`，它会产出 legacy chunk + SystemJS polyfill 并按 UA 分发。注意 legacy 模式增加产物体积与构建时间，且需要 `terser`。

### **16. `import.meta.glob` 有什么用？**

批量导入文件：`import.meta.glob('./pages/*.vue')` 默认返回懒加载函数的映射（适合路由表），加 `{ eager: true }` 变成立即导入（适合小图标集），`{ import: 'default', query: '?raw' }` 可指定导入内容。它是 Vite 特有的编译期能力，必须有字面量模式（不能是变量）。

### **17. Vite 与 Webpack 的本质区别是什么？**

Vite：dev 不打包 + 原生 ESM + esbuild 预构建，build 用 Rollup；Webpack：dev 也打包 + loader 生态覆盖所有资源，能力集中在配置里。取舍：Vite 冷启动与 HMR 有明显优势，配置更少；Webpack 在复杂定制（Module Federation、深度依赖注入、历史 loader 生态）上更成熟稳定。迁移到 Vite 的常见坑是 CJS 依赖、Node 全局变量缺失、动态 `require` 无法静态分析。

### **18. Vite 支持 SSR 吗？**

支持，但不是开箱方案：`createServer({ server: { middlewareMode: true } })` 接入 Node 服务，`ssrLoadModule` 加载服务端模块，`transformIndexHtml` 注入首屏内容；SSR 中 `import.meta.env.SSR` 可分支。实际项目多用框架封装（Nuxt、Vite SSR 插件）。

### **19. 多页应用怎么配？**

`build.rollupOptions.input` 配多个入口（`main`、`admin`），每个入口对应一个 HTML；开发时依赖 dev server 的 `appType: 'mpa'` 或按路径回退。公共依赖会由 Rollup 自动抽到共享 chunk。

### **20. Vite 的常见坑有哪些？**

首屏请求过多模块导致 dev 慢（大量 barrel 导出、整套图标库）；只用 CJS 的依赖需要 `optimizeDeps.include`；`process.env` 与 Node 全局变量在浏览器不存在；动态 `import(variable)` 无法被分析、建议用 glob 生成映射；dev 与 prod 行为差异（CSS 顺序、`require` 可用性、环境变量注入方式）；`public/` 里的文件不参与构建、不要写 `import`。

## 2、难题

### **1. 浏览器不认裸模块导入，Vite 是怎么把它变成可请求路径的？**

Vite 在 `transform` 阶段对源码做导入重写：`import vue from 'vue'` → `import vue from '/node_modules/.vite/deps/vue.js?v=hash'`；相对路径也补全为可请求的 URL（`/src/xxx.ts`）。因此浏览器拿到的代码里全是绝对路径，能直接发起 ESM 请求。这也解释了为什么“改了依赖版本要重新预构建”——重写后的路径带 hash，hash 由预构建结果决定。

### **2. 为什么首次访问常常触发“页面自己刷新一次”？**

Dev Server 是按需编译的，启动时只预构建“扫描到”的依赖（入口 HTML 与静态分析出的 import）。若某个依赖出现在动态引入、字符串拼接或运行时才能确定的路径中，浏览器首次请求到它时 Vite 才“发现”这个裸依赖，于是当场做二次预构建、把产物 hash 换掉，并通知浏览器**整页 reload** 让所有已加载模块重新指向新路径。规避方式是 `optimizeDeps.include` 预声明这些依赖。

### **3. HMR 的“失效边界”为什么能只更新局部？**

因为模块图记录了每个模块的 importer。更新时从变化文件出发，向上寻找第一个“声明了自接受”的模块（`import.meta.hot.accept`）：找到就只卸载并重新执行该模块及其下游；找不到就继续向上，直到入口则整页刷新。框架插件（`@vitejs/plugin-react`、`vue`）在组件文件里注入了 accept 逻辑与状态保留代码，所以“改组件不丢状态”。若无插件，改一个 util 文件会让引用它的整条链重新执行。

### **4. esbuild 为什么这么快，它做不到什么？**

快在 Go 编写（无 JIT 预热、可直接多核并行）、单次扫描完成解析与转译、不做完整 AST 与类型信息、内部数据结构紧凑、字符串操作复用。做不到：类型检查；对极旧语法的完整降级（target 支持有限，ES5 类特性需要额外处理）；复杂插件生态与精细分包；CSS 的一些高级处理。这正是 Vite “dev 用 esbuild、prod 用 Rollup”的原因。

### **5. dev 与 prod 双工具链会带来哪些不一致？**

四类：CSS 处理顺序与提取方式（dev 是注入 `<style>`，prod 是抽离文件）；tree shaking 与副作用判断差异（dev 不做删除）；`require`、`process.env` 等 Node 能力在 dev 可能因插件兜底可用，prod 直接报错；`define` 与 `import.meta.env` 的替换时机不同。对策是把“必须在 prod 验证”的项（环境变量、动态导入、CJS 依赖）纳入 `vite preview` 检查，而不是只看 dev 表现。

### **6. 生产构建为什么 tree shaking 效果好？**

Rollup 在打包时对所有模块做一次整体分析，基于 ESM 的静态绑定精确判断“哪些导出真的被用到、哪些语句无副作用”，并能在产物层面删除；配合 `sideEffects` 与 `/*#__PURE__*/` 注解更激进。Vite 在此之上还利用 esbuild/terser 做二次压缩。前提仍是“全链路 ESM”，一旦有 CJS 介入，分析链条就断。

### **7. 在 monorepo 里 Vite 为什么会报依赖问题？**

pnpm/npm workspace 的本地包常以**源码**形式被引用（`link:` 或 `workspace:`），Vite 默认不把它们当依赖预构建，导致其内部的裸依赖被逐个请求、甚至出现重复实例（同一库被加载两份，React Hook 报“invalid hook call”）。处理：把本地包加入 `optimizeDeps.include`、必要时 `resolve.dedupe` 去重、`preserveSymlinks` 谨慎开启、`server.fs.allow` 放开工作区目录。

### **8. Vite 上做 Module Federation 有什么限制？**

社区方案（`@originjs/vite-plugin-federation`）通过自定义运行时实现，限制较多：远程模块在 dev 下通常不可用（需要先 `build` 再 `preview`），远程方 HMR 不可靠；必须 `build.target: 'esnext'` 并开启 `topLevelAwait`；`shared` 的版本协商不如 Webpack 完善，容易出现重复加载；类型无法跨应用传递。适合“少量、边界清晰、允许刷新”的微前端场景，大规模共享仍建议 Webpack 或构建级共享（如 monorepo 公共包 + 版本锁定）。

# 一、浏览器

## 1、常见题

### **1. 浏览器的多进程架构是怎样的？**

主进程（Browser，负责标签页管理、地址栏、窗口与网络调度）、渲染进程（Renderer，负责 HTML/CSS/JS 解析与页面渲染，每个标签页一个、同站点可能共享，跨站点则强制隔离）、GPU 进程（负责合成与绘制加速）、网络进程（负责请求与缓存）、插件/工具进程。多进程的价值是**稳定性与安全隔离**（一个页面崩溃不拖垮整个浏览器，站点隔离用于缓解 Spectre 这类侧信道攻击），代价是内存占用高。

### **2. 从输入 URL 到页面显示经历了什么？**

用户输入 → 判断是搜索还是 URL（浏览器进程）→ DNS 解析 → TCP/TLS 建立连接（HTTP/2 复用、HTTP/3 走 QUIC）→ 发送请求（带缓存校验、Cookie）→ 服务端返回 → 浏览器解析 HTML 构建 DOM、请求子资源 → 解析 CSS 构建 CSSOM → 合成渲染树 → 布局 → 绘制 → 合成上屏。渲染阶段的关键是“HTML 解析是流式的、CSS 与 JS 可能阻塞”。

### **3. 渲染流程分哪几个阶段？**

DOM 树（解析 HTML）→ CSSOM（解析样式）→ 渲染树/样式计算（匹配选择器、计算层叠值）→ 布局（Layout，算几何位置）→ 分层（Layer）→ 绘制（Paint，生成绘制指令）→ 分块光栅化（Raster）→ 合成（Composite）上屏。主线程负责前段，光栅化与合成在合成线程/GPU 上，所以 `transform/opacity` 动画能绕过主线程卡顿。

### **4. 重排、重绘、合成分别是什么？**

重排（Layout）是几何变化引起的节点位置重算，代价最高且会连锁影响后代；重绘（Paint）只重画像素（颜色、背景、阴影）；合成只重排图层（`transform`、`opacity` 可走合成）。优化手段：把动画放合成层、避免在循环中读写交替、用 `contain`、减少图层数量（图层多了合成开销与显存占用都上升）。

### **5. `DOMContentLoaded` 和 `load` 有什么区别？**

`DOMContentLoaded` 在 HTML 解析完成、所有同步与 `defer` 脚本执行完毕后触发（不含图片、样式、子资源）；`load` 在页面所有资源（图片、iframe、样式）加载完成才触发，因此更晚。判断“DOM 可用”用前者，判断“首屏资源齐了”用后者；`$(document).ready` 对应前者。

### **6. 事件捕获、冒泡、目标阶段是什么？**

事件先自顶向下**捕获**（`window` → 目标），到达目标（目标阶段），再自底向上**冒泡**（目标 → `window`）。`addEventListener(type, fn, true)` 或 `{capture: true}` 在捕获阶段触发，默认在冒泡阶段。`stopPropagation` 阻止继续传播，`stopImmediatePropagation` 还阻止同元素其他监听器，`preventDefault` 阻止默认行为。不冒泡的事件：`focus/blur`、`mouseenter/mouseleave`、`load`。

### **7. 浏览器的事件循环与渲染是什么关系？**

每轮事件循环取一个任务（宏任务）执行，随后清空微任务队列，然后浏览器**按需**进行渲染（`requestAnimationFrame` 回调 → 样式计算 → 布局 → 绘制 → 合成），渲染频率受屏幕刷新率限制（一般 60Hz，即约 16.7ms 一帧）。若某个任务或微任务链执行太久，就会挤掉渲染，表现为掉帧；这也是“长任务”影响 `TBT` 的原因。

### **8. `requestAnimationFrame` 和 `setTimeout` 做动画有什么区别？**

`rAF` 在每次渲染前执行，与刷新率同步、页面隐藏时自动暂停、不受定时器最小延迟与节流影响，因此动画平滑且省电；`setTimeout` 只是“尽量在这个时间后执行”，无法与帧对齐，容易出现跳帧与抖动。动画优先 `rAF`（或用 CSS 动画），定时逻辑用 `setTimeout`。

### **9. 同源策略限制了什么？**

同源指协议、域名、端口三者一致。它限制的是**跨源的读取与交互**：`fetch/XHR` 读取响应（可发送不一定能读）、读取跨源页面的 DOM、访问跨源的 `localStorage/Cookie`、`iframe` 相互通信。**不限制**发请求本身、加载图片/脚本/样式（这正是 CSRF 与 JSONP 的基础）。同源策略是浏览器的安全模型，服务端并不执行它。

### **10. 跨域有哪些解决方案？**

服务端 CORS（首选）、开发代理（`vite` 的 `server.proxy`、nginx 反向代理，同源化）、`postMessage`（页面间通信）、`document.domain`（同主域，已废弃）、JSONP（仅 GET 且不安全，历史方案）、WebSocket（不受同源限制但服务端要校验 `Origin`）、`CORS` 配合 `withCredentials` 传 Cookie。判断标准是“能不能改服务端”，能改就 CORS。

### **11. CORS 的简单请求和预检请求怎么区分？**

满足全部条件为简单请求：方法为 `GET/HEAD/POST`，且 `Content-Type` 仅为 `text/plain`、`multipart/form-data`、`application/x-www-form-urlencoded`，无自定义头。否则浏览器先发 `OPTIONS` 预检，服务端需返回允许的方法、头与 `Access-Control-Max-Age`（缓存预检结果）。带 Cookie 时 `Access-Control-Allow-Origin` 不能为 `*`，且要 `Access-Control-Allow-Credentials: true`。

### **12. Cookie 的常用属性有哪些？**

`Domain/Path`（作用范围）、`Expires/Max-Age`（过期，缺省为会话 Cookie）、`HttpOnly`（JS 不可读，缓解 XSS 窃取）、`Secure`（仅 HTTPS）、`SameSite=Strict/Lax/None`（跨站发送策略，`None` 必须配 `Secure`）、`Partitioned`（分区存储，应对三方 Cookie 淘汰）。容量约 4KB，每次同源请求都会自动携带，因此不适合存大数据。

### **13. `Cookie`、`localStorage`、`sessionStorage`、`IndexedDB` 有什么区别？**

Cookie：约 4KB、随请求发送、可设过期、同步 API；`localStorage`：约 5MB、同源共享、永久存储、同步阻塞；`sessionStorage`：同源同标签页、关闭标签即清空、同步；`IndexedDB`：容量大（按配额）、异步、支持事务与索引、可存二进制。选型：登录态用 HttpOnly Cookie（安全），少量偏好用 `localStorage`，页面级临时数据用 `sessionStorage`，大量结构化数据用 `IndexedDB`。

### **14. `storage` 事件什么时候触发？**

同源的**其他**窗口/标签页修改了 `localStorage` 时触发（当前窗口自身不触发），可用它做跨标签页同步（如登录态、主题更新）。`sessionStorage` 不跨标签页，因此没有这种同步能力。

### **15. XSS 有哪几种类型，怎么防？**

存储型（恶意内容存到服务端，其他用户加载时执行）、反射型（随请求参数回显到页面）、DOM 型（前端把不可信数据写入危险位置，如 `innerHTML`、`location`、`document.write`）。防御：输出按上下文转义、优先 `textContent` 与安全的框架插值（不要用 `dangerouslySetInnerHTML`/`v-html` 处理用户内容）、富文本用白名单净化（DOMPurify）、CSP 限制脚本来源与内联、敏感 Cookie 加 `HttpOnly`。

### **16. CSRF 的原理和防御是什么？**

原理：用户已登录站点 A，访问恶意站点 B 时，B 诱导浏览器向 A 发起请求，浏览器**自动带上 A 的 Cookie**，服务端误认为是用户本人操作。防御：Cookie 设 `SameSite=Lax/Strict`、关键请求带 CSRF Token（服务端校验）、校验 `Origin/Referer`、敏感操作二次验证。注意 CORS 不能防 CSRF（它防的是“读取响应”，不是“发出请求”）。

### **17. CSP 是什么，怎么配？**

内容安全策略，通过响应头或 `<meta>` 声明允许加载的资源来源，是 XSS 的最后一道防线。常用指令：`default-src 'self'`、`script-src 'self' 'nonce-xxx'`、`img-src`、`connect-src`、`frame-ancestors`（防点击劫持）、`report-uri/report-to`（收集违规上报）。严格模式下禁止内联脚本与 `eval`，因此需要给内联脚本加 `nonce` 或 hash。

### **18. 浏览器缓存机制是怎样的？**

分两级：强缓存（`Cache-Control: max-age`、`Expires`）命中则直接用本地副本、不发请求（`200 from disk cache`）；协商缓存（`ETag/If-None-Match`、`Last-Modified/If-Modified-Since`）发请求校验，未变化返回 `304` 复用本地内容。实践：HTML 用 `no-cache`（每次校验，保证发版即时生效），带 hash 的静态资源用长 `max-age` + `immutable`，`ETag` 比 `Last-Modified` 更精确（但分布式部署需注意一致性）。

### **19. 常用性能指标有哪些？**

`TTFB`（首字节，反映服务端与网络）、`FP/FCP`（首次绘制/首次内容绘制）、`LCP`（最大内容绘制，核心体验指标）、`CLS`（累积布局偏移，衡量稳定性）、`TBT`（阻塞总时间，反映交互性）、`INP`（交互到下次绘制，已取代 FID）。采集用 `PerformanceObserver` 监听对应 entry，配合 `performance.getEntriesByType('navigation')` 与自定义打点。

### **20. 页面卸载时怎么可靠上报数据？**

用 `visibilitychange`（`document.visibilityState === 'hidden'`）或 `pagehide`，配合 `navigator.sendBeacon(url, data)`（浏览器接管发送，不阻塞卸载），或 `fetch(url, { keepalive: true })`。不要依赖 `unload`（移动端常不触发、且禁用同步 XHR），也不要在 `beforeunload` 里做耗时操作。

## 2、难题

### **1. 什么时候会创建合成层，`will-change` 的代价是什么？**

触发条件包括：3D 变换（`translateZ`、`translate3d`）、`will-change: transform/opacity`、`opacity` 动画、`position: fixed`、`filter`、`video/canvas`、`iframe` 等。图层能跳过主线程重绘，但每个层都要独立分配纹理显存、上传与合成开销随层数线性上升，滥用会导致“层爆炸”反而更慢。正确用法是在动画开始前声明、结束后移除，并避免给全屏大元素无脑加层。

### **2. 什么是强制同步布局，怎么避免？**

JS 修改了样式后立刻读取布局属性（`offsetWidth/offsetHeight`、`scrollTop`、`getComputedStyle`、`getBoundingClientRect`），浏览器被迫**立即**完成样式计算与布局来返回准确值，这就是强制同步布局（layout thrashing）。在循环里交替“写-读”会触发 N 次布局。解法：读写分离（先把所有读缓存下来，再统一写）、用 `rAF` 把写操作放到帧内合适时机、批量修改用 class 切换、需要测量时把元素放到离屏或先读后写。

### **3. 为什么 JS 执行要等 CSS 加载完成？**

脚本执行时可能需要读取样式（`getComputedStyle`、布局信息），浏览器为了保证拿到正确结果，会在**存在尚未加载完的 CSS 时推迟脚本执行**（CSS 阻塞脚本，但 CSS 本身不阻塞 DOM 解析）。因此“把 `<link>` 放在 `<script>` 之前”会放大首屏延迟。优化手段：关键 CSS 内联、非关键样式异步加载、脚本放 `defer/async`。

### **4. 为什么浏览器有三种“from cache”，怎么判断命中哪一级？**

常见 `from memory cache`（同一会话内、进程内存中，最快，页面关闭即失效）、`from disk cache`（跨会话、磁盘复用，需重新校验或直接命中）、`from Service Worker`（被 SW 拦截，按自定义策略返回）。DevTools 的 Size 列会标注来源；`PerformanceResourceTiming` 的 `transferSize === 0` 通常表示未走网络。策略设计要区分“能容忍多旧”的资源：HTML 走 SW/协商，静态资源走强缓存。

### **5. `SameSite` 的演进带来了什么影响？**

Chrome 80 起 `SameSite` 默认变为 `Lax`（顶层 GET 跨站请求仍带 Cookie，POST/iframe/图片等不带），直接破坏了跨站单点登录、跨域 iframe 嵌入、支付回跳等场景；三方 Cookie 又在逐步淘汰（需 `SameSite=None; Secure` 且带 `Partitioned`/CHIPS 才能在新策略下使用）。工程含义：跨站会话要转向“服务端跳转 + 短时票据”或 Storage Access API，而不是依赖三方 Cookie。

### **6. 为什么 XSS 防御不能靠黑名单？**

因为危险上下文太多且绕过方式无穷（大小写、编码、注释、`javascript:` 伪协议、事件属性、SVG、`<template>`、属性内插值），黑名单永远漏。正确做法是**按输出上下文做白名单转义**：HTML 文本用实体转义、属性用引号包裹并转义、URL 用协议白名单、JS 上下文用序列化；富文本用成熟的 DOM 树白名单净化（解析后再过滤节点与属性），并叠加 CSP 作为兜底。

### **7. 页面卸载时的上报为什么经常丢，怎么保证可靠？**

`unload/beforeunload` 在移动端与页面被系统回收时常不触发，且内部禁用同步 XHR；异步请求在卸载时可能被浏览器直接取消。可靠方案：优先在 `visibilitychange → hidden` 触发上报（iOS/Android 都能命中）、用 `sendBeacon`（浏览器保证发出、不阻塞卸载）、或 `fetch` 的 `keepalive: true`（有 64KB 体积上限），并在服务端做去重（同一会话多次上报取最后一条）。

### **8. 多进程架构对前端有哪些实际影响？**

三点：一是**共享状态不再共享**——不同标签页有各自的堆与事件循环，`localStorage` 是唯一低成本的跨标签同步手段（靠 `storage` 事件）；二是**跨进程通信有延迟**，例如 postMessage 与 Service Worker 通信是异步的，不能假设同步返回；三是**资源隔离带来性能差异**——单页面的长任务只影响自己的渲染进程，但站点隔离会让同站不同源的 iframe 分到不同进程，共享内存与缓存的能力下降。这也是“同一段代码在本页流畅、在嵌入页卡顿”的常见原因。

# 二、内存与垃圾回收

## 1、常见题

### **1. JS 的内存分为哪几块？**
三块：**栈（Stack）**存调用帧、局部变量、基本类型的值与对象的引用（指针），空间小（MB 级）、分配释放极快、后进先出；**堆（Heap）**存对象、数组、闭包、函数等动态数据，空间大（GB 级上限）、由 GC 管理；此外还有**代码空间**（存放编译后的机器码）与常量/字面量池。判断规律：大小固定、生命周期与函数调用一致的数据放栈，动态大小的放堆。

### **2. 为什么基本类型放栈、对象放堆？**
基本类型大小固定（几字节），栈上可以直接按值存放、随函数返回自动弹出，无需 GC 介入；对象大小可变、可能被多方共享、生命周期不确定，只能放堆并由引用指向，复制时只复制引用（浅拷贝语义）。这也解释了“对象赋值改的是同一份数据、基本类型赋值是独立副本”。

### **3. V8 的堆是怎么分区的？**
新生代（两个半空间，存放刚分配的对象）、老生代（老指针空间存含引用的对象、老数据空间存纯数据）、**大对象空间**（超过阈值的大对象直接进入，避免复制）、代码空间（JIT 后的机器码）、Map/单元空间（存放隐藏类等内部元数据）。分区不是学术洁癖，而是为了让“便宜算法处理大部分垃圾、昂贵算法只处理少数长期对象”。

### **4. 一个对象的“内存占用”由什么决定？**
由对象头（含指向隐藏类 map 的指针、标记位）、**in-object 属性**（直接内联在对象体内，数量有上限）、属性数组（超出部分放外部数组）、以及**元素数组**（索引属性，如类数组的 `0、1、2`）共同构成。所以“属性个数多、属性类型不一致、频繁增删属性”都会让对象变大或变慢——这是内存与性能的交汇点。

### **5. 内存的生命周期是怎样的？**
分配（声明变量、创建对象、调用函数）→ 使用（读写）→ 释放（不再可达时由 GC 回收）。前两步由代码控制，第三步**不可控**（无法指定时机、无法手动释放），这正是内存问题的根源：泄漏的本质不是“忘记释放”，而是“意外保留了不该保留的引用”。

### **6. 什么是内存泄漏？**
对象已经不再被业务需要，但仍然**从 GC Roots 可达**，因此永远不被回收，随操作次数累积。它与“内存上涨”不同：上涨可能是缓存预热、数据加载；泄漏的特征是“反复执行同一操作、GC 后仍不回落”。判断泄漏的黄金标准是“同样的操作重复 N 次，内存是否单调上升”。

### **7. 有哪些典型的内存泄漏场景？**
八类：意外的全局变量（未声明赋值、`this` 指向全局）、未清理的定时器与 `requestAnimationFrame`、未移除的事件监听（尤其绑定在 `window/document` 上）、游离 DOM（节点已从文档移除但 JS 仍持有）、闭包长期持有大对象、无上限的缓存（`Map/数组` 只增不减）、未取消的请求与订阅（Promise 链持有上下文）、以及 WebSocket/Worker 未关闭。

### **8. 什么是游离 DOM（detached DOM），怎么产生？**
DOM 节点已从文档树移除（`removeChild`、父节点被替换），但 JS 里仍持有它的引用（变量、闭包、事件回调、数组缓存），于是节点及其子树无法被回收。常见来源是“把 DOM 节点存进数组做缓存”或“事件监听里引用了节点而监听没解绑”，以及表格、图表组件销毁时未 `dispose`。它是最隐蔽的一类泄漏，因为界面上根本看不到这些节点。

### **9. 事件监听为什么容易造成泄漏？**
监听建立的是“目标 → 回调闭包”的强引用：只要监听还在，回调及其闭包捕获的所有变量都不会被回收。若监听挂在长生命周期的对象上（`window`、`document`、`body`、全局事件总线、第三方库的 emitter），组件销毁后监听仍存在，就同时泄漏了组件实例、DOM 与数据。规范做法是“谁注册谁注销”，在卸载钩子里解绑，或统一用 `AbortController` 的 `signal` 一次性取消一组监听。

### **10. 怎么查看浏览器的内存指标？**
`performance.memory` 提供 `usedJSHeapSize`（已用）、`totalJSHeapSize`（已申请）、`JSHeapSizeLimit`（上限），可用于埋点监控趋势（注意它是**粗粒度且被模糊化**的，不能当精确值）；更细的要用 DevTools Memory 面板；需要精确且可信的数据时，在跨源隔离环境下用 `performance.measureUserAgentSpecificMemory()`。

### **11. DevTools 的 Memory 面板有三种工具，怎么分工？**
`Heap Snapshot`（某一时刻的完整堆快照，用于找“谁在占内存、谁持有它”）、`Allocation Timeline`（按时间记录分配，能带**分配时的调用栈**，适合定位“哪行代码在疯狂分配”）、`Allocation Sampling`（采样式分配分析，开销小，适合长时间录制看趋势）。排查顺序通常是“先看趋势（Sampling）→ 再定位代码（Timeline）→ 最后查持有链（Snapshot）”。

### **12. 快照对比的标准流程是什么？**
拍三次：操作前的基线、执行一次可疑操作后、再执行一次同样的操作后。在 `Comparison` 视图对比“第 2 次与第 3 次之间新增且仍存活”的对象：如果在两次相同操作之后仍在持续增长，就基本确认泄漏（能排除“首次加载必然新增”的干扰）。然后按构造类型排序（`(array)`、`(string)`、自定义类）找数量异常的一类，再点开对象的 `Retainers` 看引用链。

### **13. 有哪些实用的内存优化手段？**
减少分配（热路径不建临时对象、复用对象池、避免大字符串反复拼接）、避免拷贝（用引用、用 `TypedArray`、流式处理大文件、`postMessage` 用 transferable 转移而非复制）、按需加载（虚拟列表、图片懒加载、代码分割、大数据放 `IndexedDB` 而非内存）、及时释放（置空大对象引用、`dispose` 图表与地图实例、`abort` 请求）、弱引用（`WeakMap` 存附属数据、`markRaw/shallowRef` 跳过无谓响应式）。

### **14. 大数组、大字符串处理时要注意什么？**
数组：`splice`/`shift` 会移动元素，大数组上频繁操作既慢又产生中间状态，批量处理时用双指针或 `filter` 一次生成；`slice` 复制、`subarray` 共享（`TypedArray`）。字符串：不可变，循环里 `+=` 会不断产生新字符串（引擎有 rope 优化但不保证），改用数组 `join`。二进制：`ArrayBuffer` + `TypedArray` 避免装箱，处理大文件时**分块读**而不是一次性 `arrayBuffer()`。

### **15. SPA 的内存为什么容易持续增长？**
路由切换不刷新页面，全局状态、事件总线、第三方实例、缓存都常驻；离开的页面若未清理（监听、定时器、图表实例、长轮询），其数据会一直挂着。控制手段：卸载钩子统一清理、全局缓存设上限与 LRU、`KeepAlive` 设 `max` 限制、定期用快照验证“切换 20 次后内存是否回到基线”。

### **16. 浏览器会主动回收内存吗，用户会遇到什么现象？**
会。Chrome 有标签页丢弃（Tab Discarding）与内存节省模式（Memory Saver）：后台标签页可能被冻结甚至丢弃（页面被卸载后从缓存恢复），恢复时页面重新加载、状态丢失。前端可监听 Page Lifecycle 事件（`freeze/resume`）并持久化关键状态；这也是“为什么后台标签页的定时器可能不准确”的原因之一。

## 2、难题

### **1. 隐藏类（Hidden Class / Map）是什么，为什么要关心它？**
V8 给每个对象维护一个隐藏类（描述属性布局与类型），相同结构的对象共享同一个隐藏类，属性访问因此能走“固定偏移”的快速路径。如果对象属性**增删顺序不同、类型反复变化**（如 `a.x = 1` 后又 `a.x = 'str'`），隐藏类会不断迁移或退化为字典模式，访问变慢、内存变大。工程做法：构造函数里一次性初始化所有属性（顺序固定、类型稳定）、避免 `delete`、避免动态加属性。

### **2. 快照里 Shallow Size 和 Retained Size 有什么区别？**
`Shallow Size` 是对象自身占用的字节（不含它引用的对象）；`Retained Size` 是“把这个对象回收后，能连带释放的总字节”（通过支配树计算，包含它独占支配的所有对象）。判断“谁是大户”要按 **Retained Size 排序**：一个大 Map 的 Shallow Size 很小，但它支配着成千上万条数据；而只按 Shallow 排序会误判，因为真正占内存的往往是它引用的那些数据。

### **3. `Retainers` 与 `Distance` 怎么用来定位泄漏源？**
`Distance` 是该对象到 GC 根的最短引用路径长度，值越小说明离根越近，通常越可疑（直接挂在全局或长生命周期对象上）。`Retainers` 是“谁引用了我”的反向链，从嫌疑对象逐级向上追，第一个“本不该存在”的引用节点就是泄漏源（例如 `window.__cache` → 数组 → 组件实例 → detached DOM）。技巧是先用“Detached”过滤筛出游离 DOM，再沿 Retainers 向上定位到业务代码。

### **4. 闭包为什么容易造成大对象泄漏，怎么避免？**
闭包会保留其**作用域链上被引用的所有变量**，只要闭包本身可达（例如被事件监听、定时器、全局缓存持有），它捕获的大对象就不会被释放——即使业务上早已不用。典型场景：组件里把整个 `props/state` 挂在回调上、请求回调里捕获了大响应体而回调被缓存。避免方式：只捕获必要的字段（在闭包外先做窄化）、用完置空引用、把长生命周期回调改成短生命周期（注册后在卸载里解绑）。

### **5. `ArrayBuffer`、`TypedArray`、`SharedArrayBuffer` 的内存语义有什么不同？**
`ArrayBuffer` 是一段原始二进制内存；`TypedArray` 只是它上面的**视图**（多个视图共享同一段内存，`subarray` 不复制、`slice` 才复制）；`SharedArrayBuffer` 可被多个线程（主线程与 Worker）共享，读写需要 `Atomics` 保证一致性，且要求页面处于**跨源隔离**（COOP+COEP）才可用。`postMessage` 传 `ArrayBuffer` 默认是结构化克隆（复制，大文件会翻倍占用），指定 `transfer` 才是零拷贝转移（源侧随即失效）。

### **6. `WeakRef` 能用来做“大对象缓存”吗？**
只能做“锦上添花”的缓存，不能依赖它保证释放。因为回收时机不确定（可能很久都不回收），所以 `WeakRef.deref()` 随时可能返回 `undefined`，业务必须写“未命中就重建”的路径。若要可控的缓存，应该用**显式 LRU + 上限**；`WeakMap` 更适合“给对象附加数据、对象不存在了数据自动消失”这种语义，而不是当缓存容器用。

### **7. 内存监控怎么做得可信？**
三层：本地开发用 DevTools 快照做定性判断；线上用 `performance.memory` 做**趋势**监控（明确定性是“粗粒度”，只设阈值报警不追求精度）；需要精确归因时，在跨源隔离环境下用 `measureUserAgentSpecificMemory()` 并按功能分区上报。配套要点是“按版本、按页面、按操作序列”聚合（否则不同用户环境的数据无法比较），以及把 OOM 崩溃率作为核心指标单独跟踪——因为内存问题的最终代价是崩溃与用户流失。

### **8. 前端要做内存预算，怎么定与怎么守？**
定预算：按设备分档（低端机与高端机不同上限）、按页面类型（列表页、图表页、编辑器差异大）、给出“稳态堆大小 + 允许增长速率”两个数字，而不是一个绝对值。守预算：关键操作做**重复压测**（打开关闭页面 20 次、翻页 200 次）看是否回到基线；CI 里跑内存基线脚本（Puppeteer 采集 `usedJSHeapSize`）做对比报警；线上按版本监控堆趋势与崩溃率。没有“重复操作的回落验证”，所谓内存优化往往只是把问题挪到了别处。

# 三、网络

## 1、常见题

### **1. HTTP 常见方法与幂等性怎么理解？**

`GET` 取资源（幂等、可缓存、参数在 URL）、`POST` 提交/创建（非幂等、不可缓存）、`PUT` 全量替换（幂等）、`PATCH` 局部更新（通常非幂等）、`DELETE` 删除（幂等）、`HEAD` 只要响应头（用于探测资源是否存在、大小、缓存）、`OPTIONS` 探测支持的方法（CORS 预检就用它）。幂等的实际意义是“失败后能否安全重试”，所以支付、下单这类操作用 `POST` 并配幂等键。

### **2. GET 和 POST 的本质区别是什么？**

本质是**语义**差异：GET 用于获取、应当幂等且可缓存、参数在 URL 上（会被日志与历史记录留存）；POST 用于提交、非幂等、参数在 body。常见的误解要纠正：GET 没有“长度上限”的协议规定，实际受限的是浏览器与服务器对 URL 长度的处理；两者都不“更安全”，安全取决于 HTTPS 与是否泄露敏感参数。

### **3. 常见状态码各自的含义？**

`200` 成功、`201` 已创建、`204` 成功但无内容、`206` 部分内容（Range 请求）、`301` 永久重定向（会被缓存，慎用）、`302/303` 临时重定向、`304` 协商缓存命中、`307/308` 重定向且保持方法与 body、`400` 请求格式错误、`401` 未认证、`403` 已认证但无权限、`404` 不存在、`405` 方法不允许、`409` 冲突、`429` 限流、`500` 服务端错误、`502` 网关收到无效响应、`503` 暂不可用、`504` 网关超时。排查线上问题时 `502/504` 基本指向网关与上游超时。

### **4. HTTP/1.0 和 HTTP/1.1 有什么差别？**

1.1 引入持久连接（`Connection: keep-alive` 默认复用 TCP）、管道化（请求可连续发出，但响应必须按序返回，实际很少用）、`Host` 头（支持虚拟主机，是 CDN 与多站点的基础）、分块传输（`Transfer-Encoding: chunked` 支持流式响应）、更强的缓存控制（`Cache-Control`、`ETag`）以及 `Range` 请求（断点续传、视频拖动的基础）。

### **5. HTTP/2 有哪些核心特性？**

二进制分帧（把报文拆成可交错的帧）、多路复用（一条 TCP 连接上并发多个流，解决应用层队头阻塞）、头部压缩（HPACK，静态表 + 动态表）、流优先级、服务端推送（已被主流浏览器移除）。代价是 TCP 层的队头阻塞依然存在（丢一个包会阻塞该连接上所有流），这也是 HTTP/3 的动机。

### **6. HTTP/3 用 QUIC 解决了什么？**

QUIC 基于 UDP，把 TLS 1.3 集成进握手（首次 1-RTT、会话恢复可 0-RTT），每个流独立重传，因此**单流丢包不再阻塞其他流**，彻底消除队头阻塞；支持连接迁移（用 Connection ID 标识连接，切 Wi-Fi 到 4G 不断线）；拥塞控制可插拔。代价是 UDP 在部分网络被限速/拦截，需要回退到 HTTP/2。

### **7. HTTPS 的握手过程是怎样的？**

客户端发 `ClientHello`（支持的版本、密码套件、随机数、SNI）→ 服务端回 `ServerHello` 与证书链 → 客户端校验证书（域名、有效期、签发链、吊销状态）→ 用非对称加密协商出会话密钥（TLS 1.3 为 ECDHE，1-RTT）→ 之后全部用对称加密通信。要点：**非对称只用于协商密钥与身份验证，数据传输用对称加密**（性能原因）。

### **8. 为什么需要 CA 证书，中间人攻击怎么防？**

如果只靠服务端发公钥，中间人可以替换成自己的公钥，双方都能“正常”加密通信而无法察觉。CA 通过对服务端公钥签名，客户端用内置的根证书验证签名链，从而确认“这把公钥确实属于这个域名”。所以 HTTPS 安全性依赖 CA 体系与客户端信任根；劫持安装自签根证书（企业抓包）能绕过，这也是需要校验证书链完整性、开启 HSTS 的原因。

### **9. TCP 三次握手为什么不能两次？**

两次无法确认“客户端的接收能力与服务端的发送能力”是否都正常，也无法可靠同步序列号（历史上延迟到达的旧连接请求会被误认为新连接）。三次握手让双方都确认对方能收能发，并同步初始序列号，建立可靠的双向通道。

### **10. 四次挥手与 `TIME_WAIT` 的作用？**

TCP 是全双工，需要各自关闭两个方向（FIN → ACK → FIN → ACK），因此是四次。主动关闭方进入 `TIME_WAIT` 等待 2MSL，目的是确保最后一个 ACK 能到达（若丢失对方会重发 FIN）以及让本连接的残留报文在网络中消散，避免影响后续同端口的新连接。

### **11. TCP 和 UDP 有什么区别，什么时候用 UDP？**

TCP 面向连接、可靠、有序、有流量与拥塞控制、有队头阻塞；UDP 无连接、不保证顺序与到达、头部开销小、延迟低。UDP 适合**能容忍丢包但不能容忍延迟**的场景：DNS 查询、实时音视频、游戏、以及 HTTP/3（QUIC 在 UDP 之上自己实现可靠性与拥塞控制）。

### **12. DNS 解析的完整过程？**

浏览器缓存 → 操作系统缓存与 `hosts` → 本地 DNS 服务器（递归查询）→ 根域名服务器 → 顶级域名服务器 → 权威域名服务器，逐级返回并缓存（受 TTL 控制）。优化手段：`dns-prefetch` 提前解析、减少域名数量、用 CDN 的 GSLB 做就近调度。

### **13. Cookie、Session、Token、JWT 有什么区别？**

Cookie 是浏览器的存储与自动携带机制；Session 是服务端存会话状态、客户端只存 `sessionId`（有状态、易扩展性差但可即时失效）；JWT 把用户信息签进 Token 由客户端保存（无状态、可跨服务、适合分布式），但**无法即时撤销**、体积大、且存在“`localStorage` 存 Token 遭 XSS 窃取”的风险。实践常见方案是“短效 access token + HttpOnly Cookie 中的 refresh token”。

### **14. JWT 的结构与校验方式？**

`header.payload.signature` 三段 Base64URL，靠 HMAC 或 RSA/ECDSA 签名防篡改。**payload 是明文可读的**（不能放敏感数据），服务端只需验签即可识别用户（无需查库）。因此它的安全性完全取决于签名密钥，泄露密钥等同于可以伪造任意身份。

### **15. WebSocket 是怎么建立的？**

先发一个带 `Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Key` 的 HTTP 请求，服务端返回 `101 Switching Protocols` 与 `Sec-WebSocket-Accept`（对 Key 加 GUID 做 SHA-1），之后在同一 TCP 连接上全双工传输帧。生产环境需要：心跳（`ping/pong` 或业务心跳）保活、断线重连（指数退避）、鉴权（握手时带 Token 或首帧认证）。

### **16. SSE 和 WebSocket 怎么选？**

SSE 是 `text/event-stream` 的 HTTP 长连接，**单向**（服务端推、客户端收）、只支持文本、支持自动重连与 `Last-Event-ID` 续传、走普通 HTTP（天然兼容代理与鉴权）；WebSocket 是全双工、可传二进制、但需要独立协议栈与心跳维护。判据是“是否需要客户端频繁上行”——只需要服务端推送（如 AI 流式输出、进度通知、订阅行情）用 SSE 更简单。

### **17. 轮询、长轮询、SSE、WebSocket 的演进关系？**

短轮询（定时请求，浪费与延迟并存）→ 长轮询（服务端 hold 住请求直到有数据，减少空请求但占连接）→ SSE（一条连接持续推送，自带重连）→ WebSocket（全双工）。选择依据是实时性要求、客户端是否需要上行、以及网关/代理对长连接的支持度。

### **18. 浏览器的并发请求限制是什么，域名分片还有用吗？**

HTTP/1.1 下同一域名通常限制 6 个并发连接，于是历史上有“域名分片”（把资源分散到多个子域提高并发）。HTTP/2 用单连接多路复用后，分片**反而有害**（多一条连接就多一次握手与拥塞控制，且失去头部压缩与优先级收益）。现在应减少域名、复用连接。

### **19. 队头阻塞在三个版本里的表现？**

HTTP/1.1 是**应用层**队头阻塞：同一连接上前一个响应未完成，后面的必须等待（管道化无法解决响应顺序）。HTTP/2 解决了应用层，但**TCP 层**仍有阻塞：一个包丢失会导致该连接上所有流等待重传。HTTP/3 用 QUIC 的独立流消除该问题，只剩单流内部的顺序约束。

### **20. 前端请求层要封装哪些能力？**

统一 baseURL 与超时、`AbortController` 取消（路由切换、组件卸载、重复请求）、并发控制与去重（同 key 的请求复用在途 Promise）、失败重试（仅幂等方法 + 指数退避 + 抖动）、统一错误码与提示、鉴权注入与 401 刷新令牌的排队机制、请求/响应拦截与埋点、以及响应结构校验（外部数据不可信）。

### **21. RESTful 与 GraphQL 的取舍？**

REST 以资源为中心、用 HTTP 语义表达操作、缓存与调试简单，但容易出现“多次请求拼数据”和“返回冗余字段”；GraphQL 由客户端声明所需字段、一次请求拿到多处数据、强类型 schema，代价是缓存复杂（多为 POST）、N+1 与查询深度攻击需要额外防护、服务端实现成本高。团队小、接口稳定选 REST，聚合多源、客户端形态多（多端）时 GraphQL 收益明显。

### **22. 大文件上传怎么设计？**

前端用 `Blob.slice` 分片、并发上传（控制并发数）、每片带序号与文件 hash；服务端按 hash 支持**秒传**（文件已存在直接返回）与**断点续传**（返回已上传分片列表）；全部分片到齐后发合并请求并校验整体 MD5；失败分片单独重试。配套要点是分片大小（通常 1~5MB）、并发上限、以及上传进度与取消。

## 2、难题

### **1. TLS 1.2 和 1.3 的握手差在哪？**

1.2 需要 2-RTT（先协商参数与密钥交换算法，再交换并验证），支持的密码套件繁多且有历史遗留的不安全组合；1.3 把密钥交换合并进第一次飞行，**1-RTT** 完成，删除了静态 RSA 与 CBC 等弱套件，只保留前向安全的 ECDHE，并支持会话恢复的 **0-RTT**（用预共享密钥直接发数据）。0-RTT 的风险是**可重放**，因此只能用于幂等请求。

### **2. 为什么 HTTP/2 反而可能在弱网下更慢？**

HTTP/2 把并发流塞进一条 TCP 连接，一旦发生丢包，TCP 的重传与拥塞窗口收缩会同时影响所有流；而 HTTP/1.1 的 6 条连接彼此独立，某个连接丢包只影响它自己。所以在丢包率高的移动网络下，HTTP/2 的尾部延迟可能劣于多个独立连接。这也解释了为什么 HTTP/3 要把“流”下沉到 QUIC 层。

### **3. JWT 无法撤销的问题怎么解？**

三种工程方案：缩短 access token 有效期（如 15 分钟）+ refresh token 换发（撤销只需拉黑 refresh token）；维护一个服务端的**黑名单/版本号**（用户改密或强制下线时递增版本，Token 内带版本号校验），代价是每次请求要查一次（可用 Redis 或短 TTL 缓存）；把会话状态放回服务端（退回 Session 模型）。不存在“纯无状态又能即时撤销”的方案，本质是可用性与一致性的取舍。

### **4. SSE 用 `EventSource` 有哪些硬限制，工程上怎么绕？**

`EventSource` 只能发 GET、**不能自定义请求头**（无法带 `Authorization`）、不支持请求体，跨域还需服务端配 CORS。因此需要鉴权或 POST 的场景通常改用 `fetch` + `ReadableStream` 手动解析 `text/event-stream`（可带 header、可中断、可读二进制），代价是要自己实现重连与事件解析（按 `\n\n` 分帧、处理 `data:`/`event:`/`id:`）。

### **5. 长连接的心跳间隔怎么定，为什么需要重连退避？**

心跳要小于中间设备（NAT、负载均衡、代理）的空闲超时（常见 30s~120s），通常取 30s 左右并允许服务端可配；太频繁浪费电与流量，太稀疏会被静默断开而客户端无感知。重连必须用**指数退避 + 随机抖动**（如 1s、2s、4s…上限 30s），否则服务端重启时所有客户端同时重连会造成“重连风暴”，把刚恢复的服务再打挂。

### **6. 请求重试什么情况下是危险的？**

非幂等请求（`POST` 创建订单、支付）重试可能造成重复扣款或重复下单，因此要么不重试，要么带**幂等键**由服务端去重；已经“可能成功但响应丢失”的场景（超时）最危险，因为无法区分“未处理”与“已处理”。另外重试必须区分错误类型：网络错误与 5xx 可重试，4xx（参数错误、鉴权失败）重试无意义，且要限制总次数与总时长，避免雪崩时放大流量。

### **7. CDN 的缓存与回源怎么理解？**

用户请求经 DNS/GSLB 调度到就近边缘节点，命中缓存直接返回；未命中则**回源**到源站或上级节点拉取并按策略缓存。工程要点：源站要给静态资源长 `max-age` 并用 hash 文件名（发版即改名，避免“刷新 CDN”）、动态内容用 `no-cache` 或按 `Vary` 精细缓存、回源带宽与命中率是成本核心、必要时用“预热 + 主动刷新”控制发版窗口。常见事故是源站与 CDN 对同一 URL 的缓存策略不一致，导致部分用户拿到旧版本或错误内容。

### **8. 前端如何做到“请求可取消且不留副作用”？**

统一用 `AbortController`（`fetch` 传 `signal`，axios 用 `signal`，旧的 `CancelToken` 已废弃），在路由切换、组件卸载、重复提交、搜索词快速变化时主动 `abort`；取消后要区分“用户取消”与“真实失败”（`AbortError` 不应算作错误上报），并保证取消的请求不会触发后续状态更新（在 `catch` 中判断 `signal.aborted` 直接返回）。配合“在途请求复用”（相同 key 的请求共享一个 Promise）能同时解决重复请求与竞态问题（后发请求覆盖先发结果的问题用版本号或 `abort` 旧请求解决）。

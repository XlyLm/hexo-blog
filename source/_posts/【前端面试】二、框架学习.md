# 一、React

## 1、常见题

### **1. React 的核心设计理念是什么？**

React 是 Meta 开发的、专注视图层的开源 JS 库，用来构建用户界面；核心理念：**声明式渲染、组件化、单向数据流，配合虚拟 DOM 与 diff 算法，数据变化时最小化更新 DOM**。

### **2. JSX 的本质是什么？**

是 `React.createElement(type, props, ...children)`（或新 JSX runtime 下的 `jsx/jsxs`）的语法糖，产物是描述 UI 的普通对象（React Element），不是 HTML 字符串。所以 JSX 里写 `class` 要用 `className`，`{}` 里可以放表达式但不能放语句；正因为是对象，才能被 diff、被序列化到服务端（Server Components 的传输格式）。

### **3. 类组件与函数组件有什么区别？**

类组件有实例与生命周期、`this` 上的 state；函数组件无实例、靠 Hooks 承载状态与副作用，逻辑可按“关注点”聚合而非按生命周期拆散。函数组件更易复用逻辑（自定义 Hook）、更易压缩与优化，官方主推。**追问**：不能用 Hook 的地方（错误边界）仍需要类组件，直到 React 19 提供对应 API。

### **4. 类组件生命周期分几个阶段？**

挂载：`constructor` → `getDerivedStateFromProps` → `render` → `componentDidMount`；

更新：`getDerivedStateFromProps` → `shouldComponentUpdate` → `render` → `getSnapshotBeforeUpdate`（DOM 更新前，可读滚动位置）→ `componentDidUpdate`；

卸载：`componentWillUnmount`。已废弃 `componentWillMount/WillReceiveProps/WillUpdate`（为可中断渲染让路）。

### **5. 函数组件里怎么对应生命周期？**

`componentDidMount` ≈ `useEffect(..., [])`；`componentDidUpdate` ≈ 带依赖的 `useEffect`；`componentWillUnmount` ≈ `useEffect` 的返回清理函数；`shouldComponentUpdate` ≈ `React.memo` + `useMemo`。注意语义差异：`useEffect` 在**浏览器绘制之后**执行，`componentDidMount` 在提交阶段同步执行。

### **6. state 为什么必须不可变更新？**

React 用引用比较判断是否变化（`Object.is`），原地修改对象的引用不变，依赖 `[obj]` 的 effect 与 `memo` 都不会触发；同时不可变快照让时间旅行调试、并发渲染下的旧值复用成为可能。做法：对象用展开或 `immer`，数组用 `map/filter/concat` 而不是 `push/splice`。

### **7. `setState` 是同步还是异步？**

在 React 管理的上下文（事件处理、生命周期、React 18 的 Promise/`setTimeout` 回调）中会**批处理**，多次调用合并为一次渲染，因此读到的 state 是旧值；需要立刻读取用函数式更新 `setCount(c => c + 1)`，需要同步拿到结果用 `flushSync` 强制刷新（会破坏批处理，慎用）。React 18 的自动批处理扩展到所有场景，这是相对 17 的显著变化。

### **8. `useState` 和 `useReducer` 怎么选？**

状态独立、更新简单用 `useState`；多个字段联动、更新逻辑复杂（有明确的 action 语义）、需要把更新函数传给深层子组件用 `useReducer`。判断依据是“更新逻辑能否被单独测试”，而不是状态个数。

### **9. `useEffect` 的执行时机与依赖规则？**

在 DOM 提交且浏览器完成绘制后异步执行；依赖数组按浅比较决定是否重跑；不写依赖表示每次渲染后都跑；返回函数在下一次执行前或卸载时调用（用于清理定时器、取消订阅、中断请求）。**常见坑**：依赖里放函数导致每次都是新引用（配合 `useCallback`），或故意漏依赖造成闭包旧值。

### **10. `useEffect` 和 `useLayoutEffect` 有什么区别？**

`useLayoutEffect` 在 DOM 变更后、浏览器绘制前**同步**执行，适合测量布局、读取尺寸后立刻修正 UI（避免闪烁）；`useEffect` 在绘制后执行，不阻塞渲染，适合请求、订阅、日志。代价是 `useLayoutEffect` 会阻塞绘制，服务端渲染时还会告警。

### **11. `useMemo` 和 `useCallback` 什么时候真的有用？**

`useMemo` 缓存计算结果，`useCallback` 缓存函数引用。真正有价值的场景：作为 `React.memo` 子组件的 prop、作为其他 Hook 的依赖、依赖引用不变才不会重复订阅的效果、或计算本身确实昂贵（大列表排序、复杂派生数据）。纯计算且开销小时的缓存只是增加成本；`useMemo` 也**不是语义保证**，React 有权丢弃缓存。

### **12. `ref` 有哪几种用法？**

`useRef` 存可变值（定时器 id、上一轮值，改它不触发渲染）；`ref` 绑定 DOM 后通过 `.current` 访问；`forwardRef` 把 ref 转发给子组件内部的 DOM；`useImperativeHandle` 暴露受控的方法集（如 `focus`、`scrollTo`）。React 19 起 `ref` 可作为普通 prop 传递，不再必须 `forwardRef`。

### **13. Context 的性能问题怎么解决？**

Context 的 value 变化会让**所有消费者**重新渲染，与“用到了 value 的哪一部分”无关。解法：拆分多个 Context（按更新频率）、`useMemo` 稳定 value 引用、Provider 下沉到最小子树、或改用支持选择器的方案（`use-context-selector`、Zustand/Jotai）。

### **14. 受控组件和非受控组件有什么区别？**

受控：值由 state 驱动（`value` + `onChange`），单一数据源，可校验、可联动，但每次输入都会触发渲染；非受控：由 DOM 自己维护（`defaultValue` + `ref` 读取），适合简单表单、文件输入（`file` 无法受控）、以及需要与第三方 DOM 库集成。工程取舍：复杂表单用受控 + 表单库（React Hook Form 用非受控 + ref 性能更好）。

### **15. `key` 有什么作用？**

在列表渲染的时候为同层 diff 的元素标识身份，帮助 React 复用实例与状态。没有 key 或 key 不稳定时，React 按位置匹配：插入、删除、排序会导致组件状态错位（输入框内容跟着位置走）。规则：key 在同一兄弟列表内唯一且稳定（用业务 id，只有静态列表才可用下标）。

### **16. React 的 diff 策略是什么？**

三种策略：一只对同级节点进行比较；二不同元素类型生成不同渲染树；三使用key标识子元素。

比较过程：对同级节点进行比较，类型不同则直接删除重新生成新的节点，类型相同则更新属性，然后递归比较子元素。

### **17. React 的事件机制有什么特点？**

使用合成事件（跨浏览器统一、包裹原生事件的 `SyntheticEvent`）通过在根节点统一监听原生事件，再模拟出符合 React 组件树的冒泡与捕获流程，最终调用写在 JSX 上的回调函数；React 17 起事件绑定到**根容器**而非 `document`，使多版本 React 共存与嵌套挂载不再互相干扰；React 16 的事件池（pooling）异步拿 event 会失效，已在 17 移除，事件对象可异步访问。事件冒泡在 React 树内传播，与 Portal 的 DOM 位置无关。

### **18. 错误边界能捕获什么？**

捕获子树在**渲染、生命周期、构造函数**中抛出的错误，显示降级 UI。捕获不到：事件处理函数、异步代码（`setTimeout`、Promise）、服务端渲染、错误边界自身抛出的错误。实现方式是类组件 `getDerivedStateFromError` + `componentDidCatch`（后者用于上报）。

### **19. Portal 有什么用？**

`createPortal(node, container)` 把 DOM 渲染到父组件之外的容器（弹窗、抽屉、Tooltip 避免 `overflow:hidden` 与层叠上下文裁剪），但 React 事件冒泡与 Context 仍按**组件树**工作，因此逻辑与样式不会被割裂。

### **20. 状态管理怎么选型？**

先区分两类状态：服务端状态（缓存、重试、失效）交给 React Query/SWR；客户端状态按规模分层：组件内 `useState` → 跨组件低频用 Context → 高频、细粒度更新用 Zustand/Jotai（订阅粒度小、无 Provider 嵌套）→ 复杂业务流、需要可追溯与规范约束用 Redux Toolkit（slice + immer + RTK Query）。避免“什么都往全局放”是主要判断标准。

### **21. 性能优化有哪些手段？**

渲染层面：`React.memo`（浅比较 props）、`useMemo/useCallback` 稳定引用、稳定 `key`、拆分 Context、把状态下沉到真正需要的地方（避免父级状态导致整棵重渲染）。数据层面：`useDeferredValue`/`startTransition` 让非紧急更新让路、分页与虚拟列表（`react-window`、`react-virtuoso`）。加载层面：`React.lazy` + `Suspense` 做代码分割、预取、图片懒加载。诊断靠 DevTools Profiler 看“谁在重渲染、为什么重渲染”，而不是盲目加 memo。

## 2、难题

### **1. Fiber 架构解决了什么问题？**

React Fiber 是 React 16 引入的**新一代协调引擎**，核心目标是把原来“一旦开始就无法中断”的同步渲染，改造成**可中断、可恢复、可分优先级**的异步渲染。旧版递归调用（Stack Reconciler）一旦开始就无法中断，长任务阻塞主线程造成掉帧。Fiber 把渲染拆成可中断的工作单元链表（`child/sibling/return` 指针），配合“双缓存”（`current` 与 `workInProgress` 两棵树）实现：可暂停、可恢复、可按优先级丢弃重做，渲染分“调和（可中断）”与“提交（不可中断）”两阶段。这正是并发特性（`startTransition`、Suspense）的基础。**追问**：为什么提交阶段必须同步——DOM 变更不能分批暴露给用户，否则会看到中间态。

### **2. React 18 的并发特性具体带来什么？**

自动批处理（Promise、`setTimeout` 中也合并）、`startTransition`（把更新标记为可中断的低优先级，输入与渲染可并行）、`useDeferredValue`（让派生渲染滞后于紧急更新）、`Suspense` 支持数据获取（配合框架）、`useId`（解决 SSR 与客户端 id 一致）。核心收益是“紧急交互优先”，代价是低优先级渲染可能被反复丢弃，因此更新必须是纯的。

### **3. Hooks 为什么不能写在条件或循环里？**

Hooks 的状态按调用顺序存放在 fiber 的 `memoizedState` 链表上，React 靠“第几次调用”来对应状态，没有名字。条件分支会让先后顺序错位，导致状态串位（读到别人的状态）。规则检查靠 ESLint 插件；这也是自定义 Hook 必须以 `use` 开头、且内部只能调用其他 Hook 的原因。**追问**：为什么 `useState` 返回的是数组——因为按位置取值，不需要命名。

### **4. useEffect 的“过期闭包”怎么解决？**

现象：定时器或订阅回调里读到的 state 永远是首次渲染的值。三种解法：把依赖补全（让 effect 在值变化时重建）；用 `useRef` 保存最新值（`ref.current = value` 在每次渲染时更新，回调读 `ref.current`）；把逻辑改成函数式更新 `setX(prev => ...)`。选择依据是“这个值变化时是否真的需要重建副作用”——需要重建就补依赖，不希望重建就读 ref。

### **5. `React.memo` 为什么经常失效？**

四类原因：

父组件每次渲染都传入新对象/数组/函数（引用不等，需 `useMemo/useCallback` 或用状态提升）；

`children` 每次是新元素（父的 render 产生新对象即不等）；

组件内部消费了变化的 Context（memo 不阻止 Context 更新）；

以及 `memo` 只做浅比较，嵌套对象深层变化察觉不到（需自定义 `areEqual`）。诊断方式是先确认“是不是真的需要 memo”，再用 Profiler 验证。

### **8. React 19 有哪些值得关注的变化？**

`ref` 作为普通 prop（`forwardRef` 逐步退场）、`use()` 可在渲染中读取 Promise 与 Context、Actions（表单/异步提交与 `useActionState`）、`useOptimistic`（乐观更新）、`useFormStatus`、以及对 `Suspense`/错误边界的整合；编译期优化（React Compiler）自动插入 memo，减少手写 `useMemo/useCallback`。**追问**：编译器不等于可以乱写，仍需保证组件纯、依赖正确。

### **9. 服务端组件（RSC）与客户端组件怎么划分？**

Server Components 在服务端执行、不进入客户端 bundle、可直接访问数据库与密钥、输出可序列化的 UI 描述；Client Components 用 `'use client'` 标记，承担交互与状态。划分原则：越靠叶子越用客户端（把 `'use client'` 下推到最小的交互组件），服务端负责数据获取与静态渲染。代价是 props 必须可序列化、不能用客户端 Hook、跨边界调试更复杂。

# 二、Vue

## 1、常见题

### **1. Vue 的核心设计思想是什么？**

渐进式框架 + 响应式数据驱动视图 + 组件化。核心链条是：`data` 变化 → 触发依赖该数据的渲染副作用（effect）→ 重新执行组件渲染函数 → 生成新虚拟 DOM → 与旧树对比 → 最小化更新真实 DOM。所以「改数据不用碰 DOM」是它相对直接操作 DOM 的最大差别，而「响应式 + 虚拟 DOM + 模板编译优化」是它区别于 React 的三件套。

### **2. Vue 2 和 Vue 3 的主要区别？**

响应式从 `Object.defineProperty` 换成 `Proxy`（可监听新增/删除属性、数组索引与 `length`）；API 从 Options 换成 Composition API（逻辑聚合、类型推导更好、Tree-shaking 友好）；性能优化上引入编译期标记（静态提升、PatchFlag、Block Tree），diff 从全量对比变按需对比；新增 Fragment、Teleport、Suspense、多根节点；移除 `$children`、`filters`、`EventBus` 的官方推荐地位，`v-model` 默认改为 `modelValue`。

### **3. Vue 3 的响应式原理是什么？**

`reactive` 用 `Proxy` 拦截 `get/set/deleteProperty/has/ownKeys`：`get` 时通过 `track` 把「当前正在执行的 effect」收集到 `targetMap`（`WeakMap<target, Map<key, Set<effect>>>`）里；`set` 时通过 `trigger` 取出该键对应的 effect 集合并调度执行。`ref` 用 `getter/setter` 包裹 `.value`。依赖是**按属性粒度**收集的，所以改 `obj.a` 不会触发只用到 `obj.b` 的组件更新。Vue 3.4 起对依赖追踪做了重构（减少重复收集与遍历），性能提升明显。

### **4. `ref` 和 `reactive` 有什么区别，怎么选？**

`reactive` 只能代理对象/数组，解构或整体替换会**丢失响应性**，且不能直接用于基本类型；`ref` 通过 `.value` 访问，任何类型都可用、可整体替换、可传参不丢响应性。实践：一组关联数据用 `reactive`，单值或需要跨函数传递/整体替换的用 `ref`；从 `reactive` 解构出来的字段要用 `toRef/toRefs` 包一层。

### **5. `computed` 和 `watch` 有什么区别？**

`computed` 是**派生值**，惰性求值（用到才计算）并按依赖缓存，依赖不变不重算，返回只读的 `ref`；`watch` 是**副作用**，依赖变化时执行回调，可选 `immediate`、`deep`、`flush: 'pre' | 'post' | 'sync'`。判断标准是“要一个新值用 computed，要执行动作（请求、上报、联动）用 watch”。

### **6. `watch` 和 `watchEffect` 有什么区别？**

`watch` 显式列出依赖源、能拿到新旧值、可配置 `immediate/deep`；`watchEffect` 自动收集回调中同步访问的依赖、没有旧值、立即执行一次。适合“依赖多且不确定”的场景；正因为自动收集，回调里的条件分支会导致依赖随执行路径变化，这是它不如 `watch` 稳定的地方。

### **7. 模板编译做了什么优化？**

三个阶段：`parse`（模板 → AST）→ `transform`（处理指令与优化标记）→ `generate`（AST → 渲染函数代码）。

三项关键优化：静态节点提升到渲染函数外（`hoistStatic`）避免重复创建；`PatchFlag` 标记动态节点的变化类型（如 1 文本、2 class、8 style），diff 时只比对应部分；`Block Tree` 把动态节点收集到数组，diff 时跳过静态子树。加上事件缓存（`cacheHandlers`）、`v-once`、`v-memo` 共同降低运行时开销。

### **8. Vue 3 的 diff 算法有什么特点？**

同层比较、不复用跨层级节点；按 `type` 与 `key` 判断是否为同一节点，不同则卸载重建。子节点更新分五类场景，能复用的前提下用「最长递增子序列」找出**不需要移动的节点集合**，只移动其余节点，把 DOM 移动次数降到最小。相比 Vue 2 的双端比较（四个指针 + 两端交叉查找），Vue 3 结合 `PatchFlag` 可以只对比动态属性，整体更快。

### **9. `key` 有什么用？**

标识节点身份。列表增删排序时，有正确 `key` 才能复用对应组件实例（保持内部状态与 DOM 关联）；缺省时按位置比对，表现为“输入框内容跟着位置跑”。`key` 必须在兄弟同级内唯一且稳定，用业务 id，不用随机数（每次渲染都重建）。

### **10. 组件之间有哪些通信方式？**

父子：`props` 下行、`emit` 上行、`v-model` 双向；祖先与后代：`provide/inject`（用 `InjectionKey` 保类型）；透传：`v-bind="$attrs"` 与 `inheritAttrs`；父调子方法：`ref` + `defineExpose`；任意组件：Pinia（推荐）、mitt 事件总线（小项目）；跨应用（微前端）：`initGlobalState` 或 `postMessage`。

### **11. Vue 3 的生命周期有哪些？**

`setup` 对应 `beforeCreate/created`；`onBeforeMount/onMounted`；`onBeforeUpdate/onUpdated`；`onBeforeUnmount/onUnmounted`；`onErrorCaptured`；`onActivated/onDeactivated`（配合 `KeepAlive`）。执行顺序注意：`setup` 是同步的，`onMounted` 在首次渲染提交后调用，父组件的 `mounted` 晚于子组件。

### **12. `v-if` 和 `v-show` 有什么区别，怎么选？**

`v-if` 切换组件/元素的创建与销毁，有编译期条件分支优化（不渲染的分支不进渲染函数），初始为 false 时开销小；`v-show` 只是切 `display`，元素始终渲染。频繁切换用 `v-show`，一次性或开销大的组件（含请求、重资源）用 `v-if`；`v-if` 与 `v-for` 不要同级（Vue 3 中 `v-if` 优先级更高，会导致访问不到循环项）。

### **13. 为什么 Vue 2 的 `data` 必须是函数？**

组件定义会被复用，若 `data` 是对象，所有实例共享同一引用，一个实例改状态会污染其他实例；函数每次调用返回新对象，保证实例独立。根实例可以是对象（因为只有一个）。Vue 3 的 `setup` 天然每次执行都是新作用域，这个问题不存在。

### **14. `v-model` 的原理是什么？**

Vue 3 中是 `:modelValue` 与 `@update:modelValue` 的语法糖；带参数写法 `v-model:title` 对应 `title` prop 与 `update:title` 事件；修饰符 `.trim/.number/.lazy` 由编译器生成对应的转换逻辑。自定义组件支持 `v-model` 只需声明 `modelValue` 并在 `emit('update:modelValue', v)`。

### **15. `nextTick` 的原理是什么？**

Vue 的更新是异步批处理的：数据变化后把组件的渲染 effect 放入调度队列，在微任务（`Promise.then`）里统一 `flush`（先执行 `pre` 队列，再渲染，再 `post` 队列）。`nextTick` 把回调排在同一次 flush 之后，因此能在 DOM 更新完成后执行。含义是“同一 tick 内多次改数据只渲染一次”，也意味着 `await nextTick()` 才拿得到最新 DOM。

### **16. 插槽有哪几种？**

默认插槽、具名插槽（`#header`）、作用域插槽（子组件把内部数据通过 `v-bind` 传给插槽内容，父级用 `#item="slotProps"` 接收）、动态插槽名（`#[name]`）。作用域插槽是“逻辑在子组件、渲染由父组件决定”的核心手段（如表格列自定义渲染）。

### **17. 自定义指令怎么写？**

`const vFocus = { mounted(el, binding) { el.focus() }, updated(el, binding) {}, unmounted(el) {} }`，通过 `app.directive('focus', vFocus)` 或 `directives` 选项注册；`binding` 提供 `value/oldValue/arg/modifiers`。适合处理 DOM 级行为（权限控制、拖拽、水印、复制），比组件更轻。

### **18. `mixin` 在 Vue 3 中还能用吗？**

仍支持但官方不推荐：来源不清晰（多个 mixin 同名选项合并规则容易踩坑）、与 TS 类型推导配合差。替代方案是组合式函数（`useXxx`）+ `provide/inject` + 插件，这也是 Vue 3 生态的默认实践。

### **19. Pinia 和 Vuex 有什么区别？**

Pinia 无 `mutations`（直接在 actions 里改 state）、天然支持 TS（不依赖字符串 key）、模块化即多 store 无需 `modules`/命名空间、支持 devtools 时间旅行、可按需注册；Vuex 强制 `mutation` 同步、`action` 异步，模板代码多。Vue 3 生态默认用 Pinia；获取响应式数据要用 `storeToRefs` 解构，否则丢响应性。

### **20. Vue Router 的关键点有哪些？**

模式：`history`（需服务端 fallback）、`hash`、`abstract`。能力：嵌套路由（`children` + `RouterView`）、路由懒加载（`() => import()` 天然产出分包）、动态路由（`addRoute`）、导航守卫（`beforeEach` 返回 `false` 取消、返回路由重定向）、`meta` 驱动权限与标题、`scrollBehavior` 处理滚动恢复。注意守卫里避免死循环重定向，以及组件内 `onBeforeRouteLeave` 的清理职责。

### **21. Vue 项目性能优化怎么做？**

渲染：`shallowRef` 处理大数组、`markRaw` 跳过无谓响应式、`v-memo` 缓存子树、合理用 `v-if` 避免无效渲染、`KeepAlive` 缓存频繁切换的页签。加载：异步组件 + 路由懒加载、图片懒加载、按需引入组件库与 ECharts。交互：虚拟列表处理万级数据、防抖节流、`ResizeObserver` 替代 `scroll` 轮询。诊断靠 DevTools 的组件渲染计数与 Performance 面板，先定位再优化。

### **22. ECharts 在 Vue 里怎么集成得好？**

按需引入（`echarts/core` + 具体 chart/component + 渲染器）减小体积；实例只创建一次，`setOption` 更新数据而不是重建；容器尺寸变化用 `ResizeObserver` 调 `resize()`（不是 `window.onresize`）；大数据量开 `large`、`progressive`、`sampling`；组件卸载必须 `dispose()` 并断开观察器，否则内存泄漏；`shallowRef` 存实例避免被深度代理（会显著拖慢渲染）。

## 2、难题

### **1. 分支切换为什么会产生“冗余依赖”，怎么解决？**

一个 effect 第一次执行时走 `if (ok) obj.a`，只收集了 `a`；若第二次执行改走 `else` 分支读 `b`，此时若不做清理，effect 会同时依赖 `a` 和 `b`，导致“改了不再使用的 `a` 也触发重渲染”。Vue 的做法是每次 effect 重新执行前**清理旧依赖集合**（早期用 cleanup 遍历删除，Vue 3.4 起改为更省的标记/版本机制），保证依赖集合始终反映最后一次执行的真实访问。这也是“依赖按属性粒度精确收集”必须付出的维护成本。

### **2. Vue 3 为什么用最长递增子序列，能带来什么收益？**

列表 diff 中“哪些节点能原地不动”是一个最长递增子序列问题：保留 LIS 中的节点不动，其余节点只需移动（或新建），这样移动次数最少且实现稳定。代价是需要先做一遍 key 映射与遍历，时间复杂度 O(n log n) 量级；收益是乱序列表（拖拽排序、分页数据变化）场景下比双端比较产生更少的 DOM 操作。判断标准是数据规模与乱序程度，而不是“算法更高级”。

### **3. 静态提升和 PatchFlag 在什么情况下会失效？**

静态提升只对**永不变化**的节点有效，一旦节点绑定了动态内容就退化为普通节点；`PatchFlag` 只能标记编译期可识别的动态类型（文本、class、style、props），遇到 `v-html`、动态 key、插槽、`<component :is>` 时会退化为全量对比（`PatchFlag` 为 -2 或需要完整 diff）。`Block Tree` 也有代价：动态节点过多时收集数组本身的开销上升。所以“编译优化”不是无条件的，写模板时应尽量让动态部分是明确的属性绑定，而不是整块动态结构。

### **4. 响应式丢失有哪几种典型场景，怎么修？**

三种：一是从 `reactive` 对象**解构**出基础类型（`const { count } = state`，拿到的是快照值），需 `toRefs`；二是把 `reactive` 对象整体替换（`state = {...}`，代理引用还在旧对象上），应改为逐字段赋值或用 `ref`；三是把响应式数据传进函数时被 `JSON` 序列化或 `structuredClone`（拷贝后失去代理能力）。此外用 `Object.freeze`、`markRaw` 处理的对象本就不该响应式，要区分“丢失”与“有意跳过”。

### **5. `shallowRef`、`triggerRef`、`markRaw` 分别解决什么问题？**

`shallowRef` 只对 `.value` 本身做响应式，不深度代理内部值，适合存大数组、图表实例、第三方类实例，避免深层代理带来的巨大开销与副作用；`triggerRef` 在内部数据被原地修改后手动触发更新（因为 shallow 不会自动感知）；`markRaw` 让某个对象永不被代理（如 ECharts 实例、不可变常量）。三者共同的取舍是“牺牲自动深度追踪换取性能与稳定性”。

### **6. 为什么改了数据马上读 DOM 读不到最新值？**

更新是异步批处理的：`set` 只把 effect 入队并调度到微任务，尚未 flush 渲染。因此在同步代码里读 DOM 得到旧值，需要 `await nextTick()`（或 `flush: 'post'` 的 watch）之后再读。这也解释了为什么“连续改 100 次数据只渲染一次”，以及为什么在 `onUpdated` 里读 DOM 才是最新的。注意 `flush: 'sync'` 会破坏批处理，只在确有必要的场景使用。

### **7. `KeepAlive` 缓存的组件有哪些坑？**

缓存的组件实例不销毁、DOM 不重新创建，所以 `onMounted` 不会再次触发、`onUnmounted` 也不会调用；需要使用 `onActivated`（进入）与 `onDeactivated`（离开）来启停定时器、重连 WebSocket、刷新数据。另有三个问题：缓存不设 `max` 会无限增长导致内存上涨；`key` 不稳定会导致缓存失效或命中错误实例；被缓存页面的滚动位置、`ref` 引用会持续存在，清理逻辑必须显式写在 `deactivated` 里。

### **8. 微前端（qiankun）的隔离与落地问题有哪些？**

隔离分三层：JS 沙箱（`Proxy` 沙箱为主，`legacy` 快照沙箱兼容旧浏览器）、样式隔离（`strictStyleIsolation` 用 Shadow DOM，或 `experimentalStyleIsolation` 给选择器加前缀，注意两者都不覆盖全局弹层）、资源隔离（公共依赖走 externals 或共享，避免重复加载）。落地问题：主子应用路由冲突（需约定 `activeRule` 与 basename）、通信靠 `initGlobalState` 单向且有序列化限制、跨应用鉴权与埋点需统一入口、`single-spa` 生命周期里 `mount` 失败要能降级。替代思路是“模块联邦 + 构建级共享”，代价是构建耦合度提升。
